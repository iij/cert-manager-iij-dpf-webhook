## 1. 仕様の訂正を要する事項

調査によって、spec.md の記述に事実誤認および実現不能な要件が見つかった。

### 1.1 「ラベル」の意味の誤り (訂正必須)

spec.md は「名前のラベル数には上限 10 の制約がある」と書いているが、**誤りである。**

`dpf.Record` は次の構造を持つ (`model_record.go`)。

```go
type Record struct {
    Id          string
    Name        string
    Ttl         NullableInt32
    Rrtype      RecordsRrtype
    Rdata       []RecordsRdataInner   // RRset。値の配列
    Labels      map[string]string     // ← これが「ラベル」
    State       RecordsState
    Description string                // レコード単位のコメント
    Operator    NullableString
}
```

「ラベル」は **DPF のレコードに付く key-value のメタデータ**であり、DNS 名のラベルではない。
上限 10 はこのメタデータの件数である。したがって:

- 「ラベルにカウンタを作る」案 (候補 A) は、`count.cm/<hash>` と `expire.cm/<hash>` を
  **レコードのラベルキー**として持つ案であった。1 対象あたり 2 キーを消費するため
  10 ÷ 2 = **5 対象**が上限となる。これが「最大 5 件」の根拠である。
- DNS 名のラベル数には実質的な制約はない (DNS の上限は 127 ラベル / FQDN 255 オクテット)。
  DNS 名の長さは本設計の制約にならない。
- **1 対象あたり 1 キーに収めれば 10 対象を収容できる。** 保持者ごとの記録を
  「キーに (対象, 保持者)、値に回収可能時刻」の形で持てば、キーは 1 つで足りる。
  これが最終的に採った形である (D-01, D-04)。

**訂正の影響**: 当初は「上限 10」を DNS 名のラベル数と読み、記録を別の TXT レコードに
置く設計とした (spec.md の旧 FR-057 は接頭辞付きの名前を要求していた)。
実際の制約はレコードのメタデータの件数であり、キーの設計次第で 10 対象を収容できる。
変更操作の回数を減らす必要 (§2.5 / D-15) と合わせて、記録はチャレンジレコード自身の
ラベルに置く形へ改めた。

### 1.2 チャレンジの一意識別子は存在しない (要件の実現不能)

spec.md は「当該チャレンジを一意に識別する値は、cert-manager の要求に含まれる値を
用いなければならない (MUST)」としているが、**該当する値は存在しない。**

`ChallengeRequest.UID` のドキュメントコメント
(`pkg/acme/webhook/apis/acme/v1alpha1/types.go`, v1.21.2):

```
// UID is an identifier for the individual request/response. ...
// The UID is meant to track the round trip (request/response) between the KAS and the WebHook,
// not the user request.
```

**UID はラウンドトリップ単位**であり、チャレンジ単位ではない。後片付けが再試行されれば
別の UID になるため、保持者の識別には使えない。

要求に含まれる全フィールドは
`UID / Action / Type / DNSName / Key / ResourceNamespace / ResolvedFQDN / ResolvedZone /
AllowAmbientCredentials / Config` のみ。このうちチャレンジに対して安定なのは
`DNSName` / `Key` / `ResourceNamespace` である。

**決定**: 保持者の識別子を `H(ロックオーナー, ResourceNamespace, DNSName)` とする。
ロックオーナーは配備単位の必須設定であり、クラスタを区別する。

**残余のリスク (許容)**: 同一配備・同一 namespace・同一 DNSName・同一 Key の
2 つのチャレンジが同時に走った場合、記録が 1 件に集約される。一方の後片付けが他方の分も
消すため、他方は自己確認に失敗する。cert-manager は当該チャレンジを再試行し、
再試行で `Present` が再度呼ばれて回復する。影響は遅延であり恒久的な失敗ではない。
**本仕様が解決すべき「複数クラスタ間」の事象は完全に解決される** (ロックオーナーが異なるため)。

なお上流も `Solver` インタフェースのコメントに
`// TODO: add notes about duplicate records with DNS01` を残しており、この領域が
上流でも未整理であることを示している。

### 1.3 ロックの奪取は仕様化された挙動 (要件の表現を要調整)

spec.md は「他者が保持しているロックを強制的に解放してはならない (MUST NOT)」とするが、
`utils.Mutex.Lock` は次の条件でロックを取得する (`utils/lock.go`, v0.6.0)。

- ゾーンのラベル `lock.dpf-go` が存在しない
- **ラベルが存在し、奪っても良い時刻を過ぎている**
- ラベルの値が形式を満たさない

(v0.1.0 では「owner が自分自身である」も取得の条件だったが、v0.3.0 で取り除かれた。§1.4)

すなわち**期限切れのロックは奪取する**のが設計である。これは保持者が消滅した場合に
ゾーンが永久にロックされるのを防ぐために必要な挙動であり、禁じるべきではない。

**訂正**: 「期限内のロックを奪ってはならない」に改める。期限切れロックの奪取は許容する。

### 1.4 同一オーナーでは排他が成立しない (v0.3.0 で解消済み)

**v0.1.0 の問題**: `lockable` は `owner == self` の場合にロック取得を許し、`Mutex` に
埋め込まれた `sync.Mutex` は同一インスタンスに対する呼び出しのみを直列化していた。
このため同一プロセス内で同一ゾーンに対する `Mutex` を 2 つ生成すると、両方の `Lock` が
成功し排他が成立しなかった。

**v0.3.0 で修正された。** CHANGELOG の Fixed に次のとおり記載がある。

> 同一のアクセストークンを用いる複数のプログラムの間で、ゾーン単位ロックが排他として
> 成立していなかった。DPF-API は編集中のレコードへの他ユーザからの編集を拒否するが、
> 同一ユーザからの編集は拒否しないため、ラベルの読み取りから書き込みまでの間に競合すると
> 両方が取得に成功しうる状態だった

**帰結**: プロセス内でゾーン単位に直列化する必要はなくなった (旧 D-10 を撤回)。
排他はライブラリが保証する。

### 2.2 クライアント証明書の検証

`Authorization: NewDelegatingAuthorizationOptions()` を含む。委譲認証は

そこに置かれた requestheader 用 CA でクライアント証明書を検証する
(`k8s.io/apiserver/pkg/server/options/authentication.go`)。

~~**仕様が求める「集約層以外からの接続を TLS ハンドシェイクで拒否する」は、
フレームワークが既定で提供する。**~~ **(訂正 2026-10-07)** この記述は誤りである。

### 2.3 dpf-go: ゾーンロック (v0.6.0)

`utils.Mutex` は**ゾーンのラベル 1 つ** (`utils.ZoneLockLabelKey` = `lock.dpf-go`) に
排他の情報を書き込む。値は `<保持者>-<奪ってよい時刻の 10 桁>` であり、右端から固定幅で
読むため保持者に `-` が含まれても曖昧にならない。

| API | 挙動 |
|---|---|
| `NewMutex(cr, cz, zoneID, opts...)` | **v0.6.0 で第 2 引数に `dpf.ZonesApi` が入った。**`WithOwner` / `WithTTL` / `WithLockRecordTTL` / `WithVerifyTimeout` / `WithLockRecordLabel` / `WithLockRecordContent` / `WithRenewInterval` |
| `Lock(ctx)` | **再入できない。**保持中の再取得は `ErrStillLock` |
| `LockWait(ctx, interval)` | 取得できるまで待つ |
| `Renew(ctx)` | 保持している排他の「奪ってよい時刻」を延長する |
| `Unlock(ctx)` | **保持者の確認を伴う。**保持者でなければ `ErrNotLockHolder`。**書き込みの確定を待たない** |
| `Do(ctx, fn)` | **排他を保持したまま fn を実行。実行中は自動で延長し、終了時に解放する** |
| `Owner()` | 排他の保持者を表す値 (診断用) |

| 既定値 | 値 |
|---|---|
| `DefaultLockTTL` | 15 分 |
| `DefaultLockRecordTTL` | 1 分 |
| `DefaultVerifyTimeout` | 10 秒 |
| `DefaultLockRecordLabel` | `_dpf-go-lock` |
| 延長の間隔 (`WithRenewInterval`) | 保持期間の 1/3 |
| 保持者の長さ | **1〜32 文字。**超えると書き込みを試みずに `ErrOwnerTooLong` (切り詰めない) |

**`Lock` の手順** (`utils/lock.go`):

1. ゾーンのラベルを読んで事前判定する。取得できないと分かれば一時レコードを作らずに
   `ErrStillLock` (ゾーンのラベルが上限なら `ErrLabelLimit`) を返す
2. 一時レコード (`_dpf-go-lock` の TXT) を追加予定の状態で作る (`PostRecord`)。
   追加予定が確立するまで読み戻しで待つ
3. ゾーンのラベルを読み直して判定し、書き込む (`PutZoneLabels`)。書いた値が読めるまで待つ
4. 一時レコードの追加予定を取り消す (`DeleteRecordChanges`)。消えたことを読み戻しで確かめる

**取得だけで完了を待つ変更が 3 回動く。** 各段の待ちは最長 `DefaultVerifyTimeout` (10 秒)。
この構造は v0.3.0 以来同じである (v0.5.0 までは 3 の書き込み先が SOA のラベルだった)。

**解放** (`Unlock`) は奪ってよい時刻を現在時刻へ更新する `PutZoneLabels` 1 回であり、
確定を待たない。**ラベルは削除しない** (削除すると「一度も取得されていない」状態と
区別できないため)。したがって**ゾーンのラベルを 1 つ恒久的に消費する。**

**ゾーンのラベルは未反映の編集の概念を持たない。** 取得・延長・解放のいずれもゾーンに
未反映の編集を作らず、ゾーン反映を要さない。

**`Do` の重要な性質**:

- 実行中に**排他を他者に奪われた場合、fn へ渡した context が打ち切られ** `ErrNotLockHolder`
  を返す。保護が切れたまま処理が走り続ける状態を作らない。
- 延長が「保持者でない」以外の理由で失敗した場合は次の周期で再試行する。
  **失敗が続く間は、排他が実際には失効しているのに fn が走りうる。**
- fn の panic は捕捉しない。その場合の排他は保持期間の経過で解ける。
- v0.6.0 では**一括置換を `Do` の中で行っても排他は解けない。**ただし本サービスは、
  SOA / Zone Apex NS の取り込みを止めるフラグの固定を引き受ける `ZoneApplier` を使う (D-13)。

**既定 owner ではクラスタを区別できない**点は変わらない。v0.6.0 の既定は
「ホスト名 (15 文字に切り詰め)・PID・乱数」であり、インスタンスごとに一意だが、
どのクラスタの配備かを読み取れない。仕様がロックオーナーを配備単位の必須設定としたのは
引き続き妥当である。

#### 排他の強さ (v0.6.0 で改められた)

`utils` のパッケージ文書 (v0.6.0) に次の記載がある。

> **2 者が同時に取得することはない。** ラベルの読み取りから書き込みまでの区間を専用
> レコードの追加によって排他しており、レコードの新規追加に対する同名かつ同 RRTYPE の
> 重複の拒否は編集者が誰かに依らないためである。この拒否は**ユーザをまたいで機械的に
> 効く。**
>
> **一方、保持中に他ユーザや管理画面からレコードを編集することは止められない。** 保持中の
> 尊重は、奪ってよい時刻を読んで譲るという協調によって成り立つ。

| 観点 | v0.5.0 (SOA のラベル) | **v0.6.0 (ゾーンのラベル)** |
|---|---|---|
| 2 者の同時取得 | 防がれる | **防がれる** (ユーザをまたいで効く) |
| 保持中の別ユーザ・管理画面からの編集 | DPF-API が拒否する (SOA が編集予定になるため) | **止められない** |
| 一括置換と反映 | 排他を解く | **影響しない** |
| 保持中のゾーンの状態 | SOA の未反映の編集が残る | **何も残らない** |
| 消費するラベル | SOA のラベル 2 つ | **ゾーンのラベル 1 つ (恒久)** |

**訂正**: v0.5.0 の時点で「別ユーザ (管理画面を含む) からの編集は保持中に DPF-API が
拒否する」と記録し、D-13 の残余リスクと D-16 の根拠に用いていた。**v0.6.0 ではこれが
成り立たない。**

#### 旧版との混在

v0.5.0 以前は SOA のラベルを、v0.6.0 はゾーンのラベルを見る。**新旧が同じゾーンを触ると
互いの排他を認識できず、両方が取得に成功しうる。**ライブラリは検出できない。
**同じゾーンを触るプログラムはまとめて更新する必要がある。**調査時点で同じ組織の
`external-dns-iij-dpf-webhook` は `dpf-go v0.5.0` に依存しており、同じゾーンを扱う構成では
同時に更新しなければならない。旧版が SOA に残したラベルと未反映の編集は掃除されない。

#### API 変更の経緯

- **v0.5.0**: `utils.Locker` (`Lock` / `Renew` / `Unlock`) として排他が抽象化された。
  `utils.RunLocked` が追加され、`Mutex.Do` はその薄い包みになった。`NewZoneApplier` の
  可変長引数が `utils.ApplierOption` になり、排他への設定は `utils.WithLockOptions(...)`、
  `utils.WithLockWait` は `utils.WithHoldOptions(...)` で包む形になった。
  `utils.ZoneApplier.Owner` が削除された。`utils/lockertest` が追加された
  (**本サービスは差し替えないため使わない**。D-16)。
- **v0.6.0**: `NewMutex` の第 2 引数に `dpf.ZonesApi`。`dpf.ZonesApi` に `GetZoneLabels` /
  `PutZoneLabels` が加わった (**テストで差し替える実装に影響する**)。`ErrLabelLimit` の
  意味が「ゾーンのラベルの枠が足りない」に変わった (番兵の値は同じ)。`ErrOwnerTooLong` と
  `ErrSkipApply` が追加された。`ZoneApplier` が一括置換で排他が解けることを扱う仕組みは
  取り除かれた。`NewZoneApplier` の呼び出し方は変わらない。
- `utils.DefaultRenewInterval` は 5 分。`Mutex` は保持期間の 1/3 を申告するため、
  TTL 2 分なら 40 秒ごとに延長される。

### 2.4 dpf-go: レコードとゾーン反映

| 用途 | API |
|---|---|
| ゾーン取得 (longest match) | `utils.GetZoneFromName(ctx, zonesApi, name, ...)`。`GetZoneFromZonename` / `GetZoneIDFromZonename` も内部は同じ longest match (**完全一致の関数は無い**) |
| レコード取得 | `utils.GetRecordFromZoneID` / `GetRecordFromZonename` / `GetRecordFromRecordName` |
| レコード一覧 | `RecordsAPI.GetRecordList(ctx, zoneID).KeywordsRrtype(...).ExecuteAll()` |
| レコード作成 / 更新 / 削除 | `PostRecord` / `PutRecord` / `PatchRecord` / `DeleteRecord` |
| 反映済みレコード | `GetRecordCurrents` |
| 未反映の差分 | `GetRecordDiffs` |
| ゾーン反映 (commit) | `PatchZoneChanges` (body: `PatchZoneCommit{ Description *string }`) |
| ゾーン全体の一括置換と反映 | `PatchZoneAtomicChanges` — **直接呼ばない。`utils.ZoneApplier` 経由で用いる (D-13)** |
| ゾーンのラベル | `GetZoneLabels` / `PutZoneLabels` (v0.6.0 で `dpf.ZonesApi` に追加)。**排他が用いる。本サービスは直接呼ばない** |
| 変更の破棄 | `DeleteZoneChanges` / `DeleteRecordChanges` |
| 非同期ジョブ待ち | `SyncWait` / `SyncWaitContext` / `utils.GetJobID` (`request_id` の取り出し) |

**変更系 API はすべて非同期である。** `PostRecord` / `PatchRecord` / `DeleteRecord` /
`PatchZoneChanges` / `PatchZoneAtomicChanges` はいずれも `*AsyncResponse` を返し、
`SyncWait` でジョブの完了を待つ必要がある。**変更 API の呼び出し回数がそのまま
待ち時間の回数になる。**

**同一ゾーンに対するレコード操作は並行できない。** サービス側のロックに抵触するため、
変更は逐次に行うほかない。したがって待ち時間は並列化で隠せず、回数分だけ積算される。

**`PatchRecord` は Ttl / Rdata / Labels / Description を 1 回の呼び出しで更新できる**
(`model_patch_record.go`)。`PostRecord` も Labels を含む。すなわち 1 つのレコードに対する
値とメタデータの変更は、1 回の非同期操作にまとめられる。

**ゾーン名・レコード名の正規化は dpf-go 側で miekg/dns により行われる。**
`GetZoneFromName` の longest match は `dns.IsSubDomain` と `dns.CountLabel` を用いる
(`utils/zone.go`)。**ただし本サービスは longest match でゾーンを選ばない** (D-18)。
`ResolvedZone` を渡して得たゾーンの名前が `ResolvedZone` と一致することを確かめる。

**Description は `PatchZoneCommit.Description`**。ゾーン反映時のコメントであり、
仕様が求める「本サービスによる変更であることが分かる Description」の置き場所はここである。
`Record.Description` (レコード単位のコメント) も別に存在する。

### 2.4.1 dpf-go: ZoneApplier (v0.4.0)

`utils.ZoneApplier` は、**ゾーン全体を読んで編集し、一括で置き換えて反映する**操作を
排他の下で行う。利用者が書くのは編集の内容だけである。

```go
type ZoneRecordsEditor func(ctx context.Context, records []dpf.OverwriteRecordsInner) ([]dpf.OverwriteRecordsInner, error)

func NewZoneApplier(cr dpf.RecordsApi, cz dpf.ZonesApi, cj dpf.JobsApi, zoneID string, opts ...Option) *ZoneApplier
func (a *ZoneApplier) Apply(ctx context.Context, edit ZoneRecordsEditor, opts ...ApplyOption) error
```

`Apply` の手順 (godoc より):

1. 排他を取得する (取得できない場合は `ErrStillLock`。`WithLockWait` を指定すれば待つ)
2. 公開されているレコードを取得し、リクエストの形へ変換する
3. `edit` を呼ぶ。**`ErrSkipApply` が返れば 4・5 を行わず nil を返す** (v0.6.0)。
   返された一覧が空の場合は `ErrNoRecords`
4. 一括置き換えと反映を行う (**SOA と Zone Apex の NS は取り込まない**)
5. 反映の完了を待つ
6. 排他を解放する。**解放の失敗はそのまま返る** (v0.6.0)

**往復で情報を失わない**: `currents()` は `GetRecordCurrents` の結果から
Name / Ttl / Rrtype / Rdata / Description / Labels をすべて引き継ぐ。
**編集関数の入力と出力は同じ型**であり、編集しない要素はそのまま返せばよい。
ラベル・TTL・コメントを写し忘れて失う心配がない。

**SOA と Zone Apex NS の保護**: `OverwriteSoa` と `OverwriteZoneApexNs` を**常に `false`**
で送る。利用者が変更する手段はない。CHANGELOG に次の警告がある。

> **これらの既定値は `true` であり、公開されているレコードから組み立てたリクエストを
> そのまま送ると SOA と Zone Apex の NS が意図せず置き換わる。**

`edit` の結果に SOA または Zone Apex NS が含まれない場合は変換前の一覧から補う
(`fillRequiredRecords`)。リクエストの必須項目を満たすためであり、内容には影響しない。

**排他との関係 (v0.6.0)**: 一括置き換えは**排他に影響しない。**置き換えの対象はレコードで
あり、排他の状態はゾーンのラベルにあるためである。反映の後も排他は保持され、終了時に
通常どおり解放される。

**経緯**: v0.5.0 までは排他が SOA の未反映の編集として存在し、一括置き換えがそれを解いた。
`ZoneApplier` は反映の前に自動延長を止め、反映後は排他が残っていた場合に限り解放しており、
「成功した呼び出しが解放に起因して失敗することはない」性質を持っていた。
**v0.6.0 ではこの性質は無い。**反映が完了したのちに解放だけが失敗すると、`Apply` は
エラーを返す。`Apply` は反映の失敗と解放の失敗を区別して返さない (D-15)。

**変更 API の回数**: 排他の取得 (完了を待つ 3 回。§2.3) + `PatchZoneAtomicChanges`
(完了を待つ 1 回) + 解放 (待たない 1 回)。`ErrSkipApply` で省略した場合は反映の 1 回が減る。
**回数は `dpf-go` の実装で決まり、本サービスは制御できない。**

**`ErrSkipApply` (v0.6.0)**: 編集関数が返すと、一括置換と反映を行わずに排他を解放し、
`Apply` は nil を返す。

- 省略しても、排他の取得・公開レコードの取得・解放は行われる。減るのは反映とその待ちで
  あり、**公開されているゾーンのシリアルと履歴が動かない**ことが効果である。
  **したがって排他を取らない事前判定 (D-11 の 2a/2b) は引き続き必要である。**
- 判定は `errors.Is` で行われる。包んだ場合のメッセージは捨てられる。
  `errors.Join(ErrSkipApply, 他のエラー)` を返すと省略が優先され、もう一方が失われる。
- context が打ち切られている場合は省略を成功にしない (`Apply` が `ctx.Err()` を返す)。
- 空の一覧を返すこととは別である。空は従来どおり `ErrNoRecords` (失敗)。

**v0.6.0 での呼び出し方** (v0.5.0 から変わらない):

```go
applier := utils.NewZoneApplier(cr, cz, cj, zoneID,
    utils.WithLockOptions(
        utils.WithOwner(lockOwner),   // 配備単位の必須設定 (1〜32 文字)
        utils.WithTTL(2*time.Minute), // 既定 15 分から短縮
    ),
    utils.WithHoldOptions(
        utils.WithLockWait(5*time.Second), // 取得できるまで待つ間隔。上限は ctx の期限
    ),
)
err := applier.Apply(ctx, edit, utils.WithApplyDescription(desc))
```

### 2.5 OpenAPI 定義から確定した制約

`openapi.json` (v0.1.0 同梱) の `components.schemas` から読み取った値。
**これらは推測ではなく API 定義である。**

| スキーマ | 制約 | 本設計への影響 |
|---|---|---|
| `RecordLabels` | `maxProperties: 10` | 期限の記録の収容数。他者のラベルと共有する枠 |
| `RecordLabels` の値 | `minLength: 1`, **`maxLength: 63`** | 空の値は使えない。期限の記録の値 (10 文字) は収まる |
| `RecordLabels` のキー | スキーマに制約なし。書式と長さは下記の共通ルール | `prefix/name`、prefix 253 / name 63 |
| `Description` | **`maxLength: 80`** | ゾーン反映のコメントの上限 |
| `RecordsRdata` | **`minItems: 1`**、`maxItems` なし | **RDATA が空のレコードは作れない。**件数の上限はない |
| `RecordsTtl` | `nullable: true`, `default: null`, `minimum: 1` | **null は「ゾーン既定を継承」。0 は不正** |
| `RecordsName` | `maxLength: 255` | レコード名の上限 |

**ラベルの共通ルール** (利用者提供。DPF のマニュアルより):

| 項目 | 文字種 | 長さ |
|---|---|---|
| キーの `prefix` (任意) | **DNS のドメイン名と同じ形式** | **253** |
| キーの `name` (必須) | 英数字と `.` `-` `_` | **63** |
| 値 | 英数字と `.` `-` `_` | 63 (`maxLength`) |

キーは Kubernetes のラベルと同じ `prefix/name` の形をとる。`dpf-go` のロックが用いる
`lock.dpf-go` (v0.6.0。ゾーンのラベル) は prefix を持たない `name` のみの形であり、`name` に
ドットが使えることの実例になっている。利用者が当初示した `expire.cm/<hash>` は `expire.cm` が prefix、
`<hash>` が `name` の形である。

**この書式を使う利点**: prefix に本サービスが管理する DNS 名を置けば、**キーの prefix 一致で
自分の記録を確実に識別できる。** 名前の一部を見て判別する方式より堅い。

**ロックオーナーの上限**: v0.5.0 まではロックオーナーが SOA のラベルの値として単独で
保存されたため、ラベル値の上限 63 がそのまま上限であり、`by cert-manager()` (17 文字) を
加えて 17 + 63 = 80 でちょうど `Description` の上限に一致していた。
**v0.6.0 では保持者が奪ってよい時刻 (10 桁) と区切り (1 文字) とともに 1 つの値へ詰められる
ため、`dpf-go` が上限を 32 文字と定めた** (32 + 1 + 10 = 43 ≤ 63)。Description は最大 49 文字で
上限 80 に収まる。文字種はラベル値の共通ルール (英数字と `.` `-` `_`) に従う。
`dpf-go` は文字種を検証しないため、本サービスが起動時に検証する (FR-048)。

**`RecordsRdata.minItems: 1` の帰結**: RDATA を 1 件も持たないレコードは API が受け付けない。
したがって最後の RDATA を取り除く場合は、レコードごと削除するほかない。
仕様の「RDATA が空のレコードを残してはならない」は、望ましさではなく **API の制約**である。

**`RecordsTtl` の帰結**: TTL の null (ゾーン既定の継承) と 0 は別物であり、0 は `minimum: 1`
に反して不正である。ゾーン全体を読んで書き戻す案 (D-13 案 1) で null を 0 として往復させると
API エラーまたは TTL の書き換えになる。案 1 を採らない根拠の 1 つが定義として裏付けられた。

### 2.6 dpf-go: クライアントとトークン

`utils.NewClient()` が提供するもの:

- レート制限 既定 5 req/s (burst 10)、最大同時実行数 5、リトライ 3 回、タイムアウト 30 秒。
  **RoundTripper 層で適用される。**
- `WithTokenProvider(p)` — **トークンは API リクエストごとに評価される。**
  外部でローテーションされても Client を作り直す必要がない。
  → 仕様のローテーション追随要件は、Secret を読む TokenProvider を渡すことで満たされる。
- トークン取得失敗時は `*TokenError` が返り、`Operation` はこれを**再試行しない**。
  → 仕様の「恒久的な失敗として扱い再試行しない」と一致する。

**注意点**: レート制限と同時実行数は Client インスタンスごとである。トークンが要求ごとに
異なるため Client を要求ごとに作ると、制限がプロセス全体で効かない。
→ 後述の決定 D-09 を参照。

v0.2.0 で追加された独立モジュール `github.com/iij/dpf-go/misc/k8s`。
**本プロジェクトが必要としていた処理そのものである。**

## 3. 決定事項

### D-01: 期限 (expire) による回収を採る

**決定**: 後片付けの時点では RDATA を削除せず、**期限に基づいて回収する。**
記録はチャレンジレコード自身のラベルに置き、**チャレンジコード 1 つにつき 1 つ**とする。

**経緯**: 当初は保持者ごとの記録を集合として持つ設計を採っていた (旧 D-01)。
複数のクラスタが同一のチャレンジコードを共有する場合に、一方の後片付けが他方の検証中の
RDATA を消す問題を解くためである。**期限による回収は、同じ問題を「誰も他人の RDATA を
消さない」という形で構造的に解消する。**

| 問題 | 保持者ごとの記録 (旧) | 期限による回収 (採用) |
|---|---|---|
| 複数クラスタでの同一コード | 保持者を識別して集合で管理 | **削除する動作がないため発生しない** |
| タイムアウト→再試行のずれ | 集合演算で吸収 | **後片付けが RDATA を消さないため無関係** |
| 取り残された後片付けが後続の提示を打ち消す | 期限で処理を打ち切ることが担保 | **発生しない** |
| 保持者識別値の安定性 (再試行・再起動) | 要件として必要 | **不要** |
| 同一配備・同一 namespace の同時チャレンジ | 集約される残余として許容 | **不要** |
| 1 対象あたりのラベル数 | 保持者の数 | **1** |

**代償**:

1. **使用済みの RDATA が期限まで残る。** cert-manager の `CleanUp` の文面
   (`should remove any presented challenge records`) からは外れる。ただし
   `_acme-challenge` の TXT が一定期間残ることに実害はない。ACME サーバは期待する値の
   存在のみを確認する。
2. **回収は遅延評価である。** `Present` / `CleanUp` の内部でのみ行うため、当該の名前に
   対する操作が二度と来なければ回収されない。証明書の更新が続く限りは次の提示で回収される。
3. **検証の失敗が繰り返されると記録が増える。** 失敗のたびに新しい認可が作られ、
   新しいチャレンジコードが払い出されるため。猶予を短く保つことが手当てになる (D-06)。

**`CleanUp` の副次的な利点**: 回収すべきものが 1 件もない場合、ゾーンへの変更が不要になる。
**排他の取得も反映も行わずに済み、変更 API が 0 回になる** (D-11)。

### D-02: 対象の識別値

**決定**: `SHA-256(チャレンジコード)` の先頭 64 ビットを 16 進小文字 16 文字で表す。

**根拠**: 識別値はラベルのキーとレコード内の RDATA の値を突き合わせるために用いる。
レコードは 1 つの名前に対応するため、値だけで一意に定まる。旧設計では保持者の集合を
数えるために名前を入力へ含めていたが、その必要がなくなった。

同一レコードに同時に存在する記録は最大 10 件であり、64 ビットで衝突は無視できる。

**ダイジェストは可逆でない。** 回収の際にラベルのキーからチャレンジコードを復元できない
ため、**レコード内の各 RDATA の値から識別値を計算して突き合わせる** (D-04)。

### D-03: (削除) 保持者の識別値

**撤回**: 期限による回収は保持者を区別しない (D-01)。保持者を識別する値を持たない。

cert-manager の要求にチャレンジを一意に識別する値が存在しない (§1.2) という制約は、
**この設計では問題にならない。** 旧設計ではこれが残余のリスクの源だった。

### D-04: ラベルの表現と回収の手順

**決定**: 記録 1 件をラベルの 1 エントリとして次の形で表す。

```
expire.acme.dns-platform.jp/<対象の識別値>  =  <期限 (UTC Unixtime)>
```

| 部分 | 内容 | 長さ | API 上の制約 |
|---|---|---|---|
| キーの prefix | `expire.acme.dns-platform.jp` | 27 | DNS のドメイン名の形式、最大 253 |
| キーの name | 対象の識別値 (16 進小文字 16 文字) | 16 | 英数字と `.` `-` `_`、最大 63 |
| 値 | 期限 (UTC Unixtime) | 10 | `minLength: 1`, `maxLength: 63` |

**版の扱い**: 旧設計はキーに `v1` を含めていたが、本設計では持たない。
**記録は期限で自然に消えるため、版を変えたい場合は prefix を変えればよい。**
古い prefix の記録は誰も更新しなくなり、期限の経過後に回収される。移行の手続きを要しない。

**自分の記録の判別は prefix の一致で行う。** prefix が一致しないラベルは、追加時も
削除時も維持する。

**回収の手順** (`Present` / `CleanUp` の双方で、処理の最初に行う):

1. レコードの RDATA の一覧とラベルの一覧を取得する
2. 各 RDATA の値 v について識別値 `H(v)` を計算する
3. ラベル `expire.acme.dns-platform.jp/H(v)` が存在し、その値が現在時刻を過ぎていれば、
   **v とそのラベルを取り除く**
4. 対応するラベルを持たない RDATA は**取り除かない** (本サービス以外の値でありうる)
5. 対応する RDATA を持たない期限切れのラベルは取り除く

### D-05: 記録の件数の上限

**決定**: ラベルの上限 10 件が制約となる。この枠は本サービス以外が付けたラベルと共有する。
追加によって総数が 10 を超える場合、要求を失敗させ、ログに記録する。
**他者のラベルも本サービスの記録も追い出さない。**

**旧設計との違い**: 旧設計では (対象, 保持者) の組が枠を消費したため、N クラスタが同一の
コードを共有すると N 件を要した。本設計では**対象ごとに 1 件**であり、同じ場面で 1 件で済む。

**上限に達する経路**: 同一の名前に対する検証の失敗が繰り返され、そのたびに新しい
チャレンジコードが払い出される場合。猶予の期間内に 10 を超える異なるコードが現れると
到達する。**猶予の長さが直接効く** (D-06)。到達は異常の兆候であるため、失敗させて
気付けるようにする。

### D-06: 期限の猶予と更新の閾値

**決定**: 猶予は既定 **1 時間**。**既存のラベルを更新するのは、残りが閾値 (猶予の 1/2、
既定 30 分) を下回る場合に限る。**

**猶予の根拠**: 期限が守るのは「他の実行が検証中の RDATA を回収しない」ことだけである。
必要な窓は**数分**であり、各実行の提示が期限を前進させるため窓は滑る。
1 時間は数十倍の余裕がある。

一方、猶予が長いほど使用済みの記録が残り、ラベルの上限 10 に近づく (D-05)。
**検証が繰り返し失敗すると、そのたびに新しいチャレンジコードが払い出されて記録が増える。**
cert-manager は失敗したチャレンジに対しても `CleanUp` を呼ぶが
(`pkg/controller/acmechallenges/sync.go:365` の `finalize`)、本設計の `CleanUp` は回収しか
行わないため、失敗した分の記録も猶予の間は残る。

| 猶予 | 同時検証への余裕 | 失敗が繰り返された場合の蓄積 |
|---|---|---|
| 24 時間 | 数百倍の過剰 | 再試行が 1 時間間隔なら**約 10 時間で上限に到達**。回復にも 24 時間かかる |
| **1 時間 (採用)** | 数十倍の余裕 | 1〜2 件で頭打ち |

**閾値の根拠 (再試行ストームへの配慮)**: 当初は提示のたびに期限を更新する設計だったが、
**再試行のたびに反映を行うことになり、費用が釣り合わない。**

- 同一ゾーンへのレコード操作は**並行できない**。無駄な反映は直列の待ち行列を作り、
  各回が排他を保持する。再試行が重なるとゾーンが占有され、本来の処理が進まない。
- 再試行の時点では、元の提示が数分前に設定した期限がそのまま残っている。
  **更新しても窓はほとんど前進しない。** 得るものがない。

閾値を猶予の 1/2 とすると、**元の提示から 30 分以内の再試行は変更 API 0 回**で終わる。

**「RDATA があれば即終了」としない理由**: RDATA はあるがラベルが無い場合、そこで打ち切ると
ラベルが永久に作られない。対応するラベルを持たない RDATA は回収の対象にならない (D-04)
ため、**その RDATA は二度と回収されなくなる。** 旧版からの移行や手動での追加で起こりうる。
判定は「RDATA の有無」ではなく**望む最終状態と現状の一致**に置く (D-11)。

**競合の観点**: 判定を排他の外で行ってよいのは、ラベルの残りが閾値以上であれば
その RDATA が他の実行に回収されないためである。回収は期限切れに限られる。
判定と実行の間に状態が変わる経路がない。

### D-07: ポート

**決定**: webhook は `--secure-port` の既定 **443** を用いる。healthz と metrics は
**別ポート 8080** で独自の HTTP サーバとして提供する。

**根拠**: 443 はフレームワークの既定であり、APIService の Service ポートとしても慣例。
フレームワーク自身も `/healthz` と `/metrics` を secure port 上に持つが、これらは
委譲認証の対象であり probe とスクレイプはクライアント証明書を提示できない。
憲章および仕様が求める「webhook と exposed を同一ポートにしない」を満たすため、
認証を要しない別ポートを自前で立てる。

**追記 (実装時)**: コンテナは `--secure-port=10443` で待ち受け、Service が **443** で公開する。
APIService から見たポートは 443 のまま変わらない。非 root かつ capability をすべて落とした
コンテナ (`restricted`) は、1024 未満のポートを確実には待ち受けられない
(`net.ipv4.ip_unprivileged_port_start` はコンテナランタイムに依存する) ためである。

### D-08: RBAC

**決定**: 次の 3 つに限る。

| 用途 | 対象 | 動詞 | 範囲 |
|---|---|---|---|
| 集約層の CA 取得 | `configmaps` (`extension-apiserver-authentication`) | `get`, `list`, `watch` | `kube-system` の Role |
| 認証・認可の委譲 | `tokenreviews`, `subjectaccessreviews` | `create` | ClusterRole (`system:auth-delegator` の内容) |
| トークン取得 | `secrets` | `get` のみ | 対象 namespace の Role、または ClusterRole |

`list` / `watch` は `extension-apiserver-authentication` ConfigMap に限り許す
(委譲認証が informer を用いるため)。**Secret に対する `list` / `watch` は許さない。**
APF が無効 (§2.1) のため `flowcontrol.apiserver.k8s.io` の権限は不要。

### D-09: トークンの取得と DPF クライアントの共有

**トークンの取得**: `github.com/iij/dpf-go/misc/k8s` の `NewTokenProvider` を用いる (§2.7)。
自前で Secret 読み出しを実装しない。解決した namespace / Secret 名 / キーを
`WithNamespace` / `WithSecretName` / `WithKey` で渡す。namespace は必須であり、
本サービスは `AllowAmbientCredentials` による分岐で解決した値を明示的に与える。

エラーの分類はモジュールが返す型で行う。

| エラー | 分類 |
|---|---|
| `ErrSecretNotFound` / `ErrKeyNotFound` / `ErrEmptySecret` / `ErrForbidden` | 恒久的な失敗。再試行しない |
| それ以外 (到達失敗など) | 一時的な失敗。上限付きで再試行してよい |

ローテーション追随は `QueriesEveryCall` (呼び出しのたびに問い合わせる) によって満たされる。

**クライアントの共有**: レート制限・同時実行数・リトライを**プロセス全体で 1 つ**にする。
`utils.NewClient` を 1 つだけ作り、`WithTokenProvider` に「現在処理中の要求に対応する
トークンを返す provider」を渡す形は取らない (要求が並行するため provider が
どの要求のトークンを返すべきか決まらない)。

代わりに、**トークンの出所 (namespace, Secret 名, key) をキーとする Client のキャッシュ**を
持ち、同一の出所に対しては Client を再利用する。レート制限がキャッシュごとに分かれる問題は、
`WithHTTPClient` に**共通の RoundTripper を注入**して 1 つの制限を共有させることで解決する。

**根拠**: トークンは要求ごとに決まる (テナントごとに異なる) ため、単一の Client では
表現できない。一方レート制限は相手のサービスに対する配慮であり、プロセス全体で
1 つでなければ意味がない。

### D-10: プロセス内直列化は行わない (撤回)

**決定**: 撤回する。ゾーン単位のプロセス内直列化は行わない。

**経緯**: v0.1.0 では同一オーナーの `Lock` が両方成功し排他が成立しなかったため、
プロセス内で直列化する決定を置いていた。**v0.3.0 で修正された** (§1.4)。
排他はライブラリが保証する。

`utils.Mutex` は `NewMutex` ごとに異なる owner を持ち、`Lock` は再入できない。
同一プロセスから同一ゾーンへ並行して操作しても、一方が `ErrStillLock` となる。
`WithLockWait` を指定すれば取得できるまで待つ。

### D-11: 変更の適用手順

**決定**: `utils.ZoneApplier.Apply` に委ねる。1 回の `Present` / `CleanUp` は次のとおり。

| # | 操作 | 変更 API | 完了を待つ |
|---|---|---|---|
| 1 | `ResolvedZone` と一致する DPF のゾーンを特定する (`utils.GetZoneFromName` の結果の名前が `ResolvedZone` と一致することを確かめる。longest match の結果をそのまま使わない。D-18) | | |
| 2 | `domainFilters` を判定する。一致しなければ何も変更せず失敗 | | |
| 2a | **変更の要否を、公開レコードを読んで判定する** (排他を取らない) | | |
| 2b | **望む最終状態が現状と一致すれば、ここで終える。変更 API は 0 回** (D-06) | | |
| 3 | `ZoneApplier.Apply` を呼ぶ | | |
| 3a | └ 排他を取得する (`WithLockWait` で待つ)。一時レコードの作成・ゾーンのラベルの書き込み・一時レコードの取り消し | ○ ×3 | ○ ×3 |
| 3b | └ 公開レコードを取得する (`GetRecordCurrents`) | | |
| 3c | └ 編集関数で期限切れを回収し、`Present` なら Rdata とラベルを加除する。**結果が入力と変わらなければ `ErrSkipApply` を返す** | | |
| 3d | └ 一括置換と反映 (`PatchZoneAtomicChanges`)。3c で省略した場合は行わない | ○ | ○ |
| 3e | └ 排他を解放する (ゾーンのラベルの書き込み) | ○ | |

- 編集関数は**受け取った一覧のうち、対象のレコード以外をそのまま返す。**
  ラベル・TTL・コメントは同じ型で往復するため失われない (§2.4.1)。
- `domainFilters` の判定 (2) は、対象ゾーンが確定した時点で行う。
  編集関数の中でも、書き込み対象のレコードを組み立てる直前に再度確認する。
- RDATA が 1 件も残らない場合は、編集関数が当該レコードを一覧から除いて返す。
  `RecordsRdata` の `minItems` が 1 であるため、空の RDATA を持つレコードは返せない。
- 期限切れの記録の回収は編集関数の中で行う (メモリ上の操作であり API を要さない)。
- **3c の省略が効くのは、2a の判定の後に状態が変わった場合である。**典型は、先の処理が
  タイムアウトの後も走り続けて完了し、その間に来た再試行が排他を待っていた場合である
  (D-15)。
- `Apply` の中で排他を奪われた場合、編集関数へ渡された context が打ち切られ
  `ErrNotLockHolder` が返る。**保護が切れたまま書き込むことはない。**

**`utils.Mutex.Do` は使わない。**v0.6.0 では一括置換が排他を解かなくなったため、`Do` の中で
行っても解放は失敗しない。しかし SOA と Zone Apex NS の取り込みを止めるフラグの固定を
自前で持つことになるため、`ZoneApplier` を使う判断 (D-13) は変わらない。

**追記 (実装時)**: 新たに作成するチャレンジレコードの TTL は **60 秒** (定数 `dpf.ChallengeTTL`) とする。
仕様は「TTL を定めるのは新規作成時のみ」(FR-032) と定めるが値を定めていない。期限による回収で
RDATA の集合が時間とともに変わるため、古い集合がリゾルバに長く残らないよう短くする。
既存のレコードへの追記では TTL を変えない。TXT の RDATA は引用符で囲んだ形 (`"<チャレンジコード>"`)
で置く (dpf-go の一時レコードと同じ表記)。**この表記で DPF が受け付け、権威サーバから期待どおりに
応答されることは実環境の検証 (T075) で確かめる。**

### D-13: ゾーン全体の置換を `ZoneApplier` 経由で用いる

**決定**: `utils.ZoneApplier.Apply` を用いる。
`PatchZoneAtomicChanges` を直接呼ばない。

**経緯 (v0.1.0 時点の判断を改めた)**: 当初はレコードを 1 つずつ編集して
`PatchZoneChanges` で反映する案を採り、ゾーン置換を退けていた。退けた根拠は 3 つあった。

| 当初の根拠 | v0.4.0 での状況 |
|---|---|
| 往復で TTL の null・未知の RRTYPE・項目の写し漏れが起こり、範囲外のレコードが壊れる | **解消。** 編集関数の入力と出力が同じ型であり、編集しない要素はそのまま返せばよい (§2.4.1) |
| 反映がその時点で排他を解くため、読み出しから書き戻しまでの保護が崩れる | **解消。** v0.4.0〜v0.5.0 は `ZoneApplier` が反映の前後を扱った。**v0.6.0 では反映が排他に影響しない** |
| 影響範囲がゾーン全体になる | **残る。** ただし SOA と Zone Apex NS は `false` 固定で保護される |

あわせて、当初の案にも見落としがあった。**`PatchZoneChanges` はゾーン内の編集中の変更を
すべて反映する。** すなわち他者が積んだ未完了の編集も適用してしまう。一方ゾーン置換は
他者の未反映の編集を破棄する。**どちらも排他に参加しない変更者に対して無害ではない。**
当初の案が一方的に安全だという前提は誤りであった。

**採る根拠**:

1. **排他の中の変更が反映 1 回で完結する。** 逐次編集の案ではレコード変更と反映で
   完了を待つ変更が 2 回以上要った。DPF の変更系 API は非同期で 1 回 10 秒以上を要し
   同一ゾーンでは並行できないため、回数の差がそのまま処理時間の差になる (D-15)。
2. **往復の取りこぼしという最大の危険をライブラリが引き受ける。** 自前で組めば
   `overwrite_soa` / `overwrite_zone_apex_ns` の既定が `true` である罠も踏みうる。
3. 排他と反映の前後関係という扱いの難しい部分も、ライブラリの内側に収まる。

**残る危険と受容**:

- **ゾーン全体を読む。** 大きいゾーンではページングで取得の呼び出しが増える。
  取得は同期であり非同期ジョブの待ちを伴わないが、レート制限の対象にはなる。
- **他者の未反映の編集を破棄する。** 排他に参加しない変更者が編集中の状態にしている場合に
  起こる。v0.5.0 の時点では「保持中は別ユーザが編集中の状態を作れないため窓は狭い」と
  評価したが、**v0.6.0 ではこの評価が成り立たない** (§2.3)。保持中も他ユーザ・管理画面から
  編集できるため、**利用者が管理画面で編集中の変更は、本サービスの反映によって失われうる。**
  窓は反映 1 回の間であり、`CleanUp` の大半と閾値内の再試行は反映を行わない (D-06) ため
  頻度は低い。受容するが、運用上の注意として利用者文書に記す。
- **機構としてはゾーン全体を書き換える。** 編集関数が対象以外をそのまま返す限り内容は
  変わらないが、編集関数の誤りがゾーン全体に及ぶ。**編集関数を小さく保ち、
  対象以外に触れないことを単体テストで固定する。**

### D-14: 中断時の残留への対処 (簡素化)

**決定**: 変更を積む工程が無くなったため、積んだ変更の破棄は不要になった。

**経緯**: 逐次編集の案では、変更を積んでから反映するまでの間に中断すると編集中の変更が
残り、`DeleteRecordChanges` による破棄と、次回のロック取得後の積み直しが必要だった。
`ZoneApplier.Apply` は取得・編集・置換を 1 つの呼び出しで行い、**編集中の状態を
経由しない。** 中断した場合、live なゾーンは無変更のまま残る。

**残るもの**: 排他の取得に用いる一時レコード (`_dpf-go-lock` の TXT) は、取得の途中に
他者がゾーン反映を行うと権威サーバへ公開されることがある。v0.6.0 では一時レコードが
存在するのは取得の途中だけであり、窓は短い。**公開された場合もライブラリが自力で回復する。**
次の `Lock` がそのレコードを削除予定にしてから入れ直す。本サービスが扱う必要はない。

### D-15: 時間予算と呼び出し元のタイムアウト

**事実** (利用者確認済み): DPF の変更系ジョブ 1 回の完了時間は **10 秒以上**である。
ゾーン反映の所要時間は、編集していないレコードも含めたゾーン全体のレコード数に影響される。
同一ゾーンに対するレコード操作は並行できないため、待ち時間は積算される。

**決定した経路 (D-11) の変更 API**:

| # | 操作 | `Present` | `CleanUp` (回収なし) | 完了を待つ |
|---|---|---|---|---|
| 0 | 公開レコードの読み出しによる要否の判定 | ○ | ○ | — (変更 API ではない) |
| 1 | 排他の取得 (`ZoneApplier` の内側)。一時レコードの作成・ゾーンのラベルの書き込み・一時レコードの取り消し | ○ ×3 | **行わない** | ○ ×3 (各最長 10 秒) |
| 2 | 一括置換と反映 (`PatchZoneAtomicChanges`)。ゾーンの規模に依存 | ○ | **行わない** | ○ |
| 3 | 排他の解放 (ゾーンのラベルの書き込み) | ○ | **行わない** | 待たない |

**完了を待つ変更が 4 回あり、回数は `dpf-go` の実装で決まる。**反映 1 回が 10 秒以上を要し、
排他の取得の各段も最長 10 秒待ちうるため、**1 回の処理が 60 秒を越えることは通常の経路として
起こりうる。**

**経緯**: 当初は「排他の取得 1 回 + 反映 1 回 = 変更 API 2 回」と数え、60 秒に収めることを
前提に成功基準 (旧 SC-002) を置いていた。**これは数え誤りであった。**排他の取得は v0.3.0
以来、一時レコードの作成・ラベルの書き込み・一時レコードの取り消しの 3 回からなる。
回数を本サービスが減らす余地は無く、**60 秒に収める設計は成り立たない。**

**`CleanUp` は通常 0 回で済む。** 期限切れの回収すべきものが無ければゾーンへの変更が
不要であり、排他も反映も行わない (D-01 / D-11)。読み出しのみで完結する。

**`Present` の再試行も通常 0 回で済む。** 元の提示が設定した期限の残りが閾値以上であれば
変更が生じないため (D-06)。**再試行ストームがゾーンを占有しない。この性質が、下記の
「タイムアウトを前提とした収束」の要である。**

#### 要求のタイムアウト (60 秒) の出典

cert-manager 側の webhook 呼び出しは `Do(context.TODO())` であり、明示的なタイムアウトを
設けていない (`cert-manager@v1.21.2/pkg/issuer/acme/dns/webhook/webhook.go:52,88`。
同ファイルに `Timeout` の指定はない)。したがって上限は apiserver 側の設定で決まる。

**既定値の出典**: `k8s.io/apiserver@v0.36.2/pkg/server/config.go:453`
(cert-manager v1.21.2 が `go.mod` で依存するバージョン)。

```go
RequestTimeout: time.Duration(60) * time.Second,
```

これは `server.NewConfig()` が返す既定であり、`pkg/server/options/server_run_options.go:124`
の `defaults := server.NewConfig(...)` を経て `--request-timeout` フラグの既定値になる。

**適用箇所**: 同 `config.go:1090`。

```go
handler = genericapifilters.WithRequestDeadline(handler, c.AuditBackend, c.AuditPolicyRuleEvaluator,
    c.LongRunningFunc, c.Serializer, c.RequestTimeout)
```

**この既定は kube-apiserver 固有ではない。** `server.NewConfig()` を使うすべての apiserver に
効く。本サービスも `genericoptions.NewRecommendedOptions` (§2.1) を経て同じ既定を持つため、
**60 秒の壁は 2 箇所にある。**

| 位置 | 効果 | 本サービスから変更できるか |
|---|---|---|
| kube-apiserver (集約層) | cert-manager からの要求を 60 秒で打ち切る | **できない** (クラスタの設定) |
| **本サービスの apiserver** | 自分が受けた要求を 60 秒で打ち切る | できる (`--request-timeout`) |

本サービス側だけを延ばしても、集約層が 60 秒のままなら呼び出し元から見た上限は変わらない。
**呼び出し元から見た上限は 60 秒**である。

**タイムアウトしても処理は止まらない**: 同 `config.go:1088` の
`WithTimeoutForNonLongRunningRequests` のコメントに次の記載がある。

> The go-routine can keep running, while the timeout logic will return a timeout to the client.

すなわちクライアントへタイムアウトを返したあとも、ハンドラの goroutine は走り続ける。
当初はこれを「排他を保持したまま放置される経路」として、自前の期限を 60 秒より短くする
ことで塞ごうとした。**v0.6.0 の改版で、この性質を逆に利用する方針へ改めた**
(下記の決定)。処理は呼び出し元のタイムアウトの後も完了まで進み、再試行が完了した状態を
見つける。

#### タイムアウト後も処理が続くことの帰結

apiserver はクライアントへタイムアウトを返したあともハンドラの goroutine を止めない。
このため次の経路が生じる。

1. `Present` が 60 秒を越える
2. 集約層がクライアント (cert-manager) にタイムアウトを返す
3. **本サービスの処理は続き、最終的に成功しうる**
4. cert-manager は失敗と見て再試行する。**再試行の時点で記録とレコードは既に存在する**

`CleanUp` でも同じことが起こる。

##### 期限切れの context では排他を解放できない (要件の訂正)

`RunLocked` は解放を**外側の ctx** で行う (`utils/locker.go`, v0.6.0)。

```go
fnErr := fn(hctx)
h.stopRenew()
lostErr := h.lostError()
relErr := releaseLock(ctx, l)   // ← hctx ではなく ctx。releaseLock は l.Unlock(ctx) のみ
```

`context.WithoutCancel` はパッケージ内のどこでも使われていない。

**したがって、本サービスが操作期限付きの context を渡し、その操作期限が切れた場合、
`Unlock` の API 呼び出しも同じ期限で失敗し、排他は解放されない。**
排他は TTL の満了まで残る。

**訂正**: 「操作期限に達した場合、ロックを解放してからエラーを返すこと (MUST)」は実現できない。
解放の試行は行うが、失敗した場合は TTL による失効に委ねるほかない。
**TTL を短く保つこと (既定 2 分) が、この経路に対する手当てである。**

##### 反映の後に解放だけが失敗した場合 (v0.6.0)

v0.6.0 の `Apply` は反映の後に通常どおり解放し、**解放の失敗をそのまま返す** (§2.4.1)。
反映の失敗と解放の失敗は区別して返されない。

**決定**: 区別しない。`Apply` がエラーを返せば、反映が完了していても要求の失敗として返す。

- 再試行は 2a/2b (D-11) で望む最終状態を見つけ、**変更 API 0 回で成功する。**
  失敗として返しても害がない。
- 区別するにはエラーの種類から推測するか、`Apply` を使わずに `RunLocked` で自前に組む
  必要がある。前者は脆く、後者は D-13 を崩す。
- 排他は TTL の満了で失効する。
- 操作期限を長く取る (下記の決定 2) ため、期限切れの context による解放の失敗は
  まれである。

##### 期限による回収がこの経路を吸収する

| 方式 | `Present` の再試行 | `CleanUp` の再試行 |
|---|---|---|
| 整数カウンタ (検討のみ・不採用) | 1 → 2 に**ずれる**。以後 RDATA が永久に消えない | 0 → -1 に**ずれる**。他の実行が必要とする RDATA を消しうる |
| 保持者ごとの記録 (旧案) | 同一のキー → 時刻のみ更新。ずれない | 既に不在 → 何もしない。ずれない |
| **期限による回収 (採用)** | RDATA は重複せず**期限のみ更新**。ずれない | **回収しか行わない。**期限切れが無ければ何も起きない |

**採用した設計では、そもそも「ずれる量」が存在しない。** 後片付けが削除を行わないため、
呼ばれた回数が状態に影響しない。

##### 取り残された `CleanUp` が後続の `Present` を打ち消す危険はない

旧案 (保持者ごとの記録) では、取り残された `CleanUp` が後続の `Present` の記録を消し、
RDATA まで削除しうる経路があった。**本設計では `CleanUp` が削除を行わないため、
この経路は存在しない。**

取り残された `CleanUp` が後から実行されても、行うのは期限切れの回収だけである。
後続の `Present` が期限を前進させているため、その対象は回収されない。

**保持者の識別値が再試行や再起動をまたいで安定である必要もない。** 保持者を持たないため。

#### 決定

1. **1 回の処理が要求のタイムアウト (60 秒) に達することを前提とする。**
   呼び出し元へタイムアウトが返ったのちも処理を完了まで進め、cert-manager の再試行が
   望む最終状態を見つけて変更を行わずに成功する (D-06 / D-11) ことで収束させる。
2. **`Present` / `CleanUp` には `context.Context` が渡されない** (`webhook.Solver` の定義)。
   本サービス自身が操作全体に期限 (**操作期限**) を設ける。**操作期限は 60 秒より長くし、既定 5 分とする。**
   操作期限の役割は、取り残された処理が走り続ける時間に上限を設けることである。
   既定値は、完了を待つ 4 回の変更 (§2.3 の各段最長 10 秒 + 反映) と排他の待ちを覆う長さとして
   置き、T012 の実測で見直す。
3. **操作期限の context は要求の context から派生させない。**派生させると呼び出し元の
   タイムアウトで処理が打ち切られ、完了しない処理が再試行のたびに繰り返されて収束しない。
4. **期限は context として `ZoneApplier.Apply` へ渡し、DPF への呼び出しまで伝播させる。**
   操作期限を越えて書き込まない。
5. **操作期限に達した場合、排他の解放は失敗する** (上記)。解放の試行は行うが、成否に依存しない。
   排他は TTL の満了で失効する。
6. **ロックの TTL を `dpf-go` の既定 15 分から短くし、2 分とする。**
   `Apply` は実行中に自動で延長する (40 秒ごと) ため、操作が長引いても失効しない。
   一方、保持者が消滅した場合に他をブロックする時間は TTL で決まる。
7. **排他を取得できない場合は 5 秒間隔で待つ** (`WithLockWait`)。待機の上限は操作期限
   である。先の処理が走っている間に来た再試行は排他を待ち、取得後に読み直して変更不要なら
   `ErrSkipApply` で反映を省く (D-11 の 3c)。
8. **本サービスの `--request-timeout` は既定 (60 秒) のままとする。** 延ばしても集約層が
   60 秒のままなら呼び出し元から見た上限は変わらない。処理はこの打ち切りの後も続くため、
   延ばす利点がない。

#### 収束の流れ

```
1 回目の Present ─ 排他の取得 ─ 反映 ─ 解放 ─ 完了
   │ 60 秒
   └→ 呼び出し元へタイムアウト
        cert-manager が再試行
          ├ 1 回目が完了済み   → 2a/2b で変更不要 → 変更 API 0 回で成功
          └ 1 回目が走行中     → 排他を待つ → 取得後 3c で変更不要 → 反映せず成功
                                   (期限までに取得できなければ一時的な失敗 → 次の再試行)
```

**再試行が重なっても状態はずれない** (下記「期限による回収がこの経路を吸収する」)。

#### 成功基準

処理時間は DPF のジョブ完了時間とゾーンの規模に支配され、本サービスが制御できない。
基準を、本サービスが制御できる量に置く。**変更 API の回数による基準は置かない**
(回数は `dpf-go` の実装で決まるため。旧 SC-002 を撤回)。

- **変更が不要な操作で変更 API が 0 回であること** (回収すべきものが無い `CleanUp`、
  閾値の期間内の `Present` の再試行)
- **1 回の処理が 60 秒を越えても、再試行を経て証明書の取得が完了すること**
- ジョブ待ちを除いた本サービス自身のオーバーヘッドが 5 秒以内であること
- **操作期限に達した場合に、操作期限を越えて DPF への書き込みが行われた件数が 0 件であること**
- **タイムアウトと再試行を経ても、記録の数と RDATA の数がずれた件数が 0 件であること**

#### 残余のリスク

- **取り残された処理が同時に複数走りうる。**再試行のたびに新しい処理が始まり、先の処理が
  排他を保持していれば後の処理は待つ。上限は操作期限 (既定 5 分) で決まる。
  同一ゾーンに対する待ちの goroutine が一時的に積み上がるが、各々は期限で終わる。
- **証明書の取得が遅延する。**1 回目がタイムアウトした場合、完了は cert-manager の再試行の
  間隔に依存する。恒久的な失敗にはならない。

### D-16: 排他は既定の実装を使い、差し替えない

**決定**: `utils.Locker` による差し替えを行わない。既定のゾーンのラベルを用いる
`utils.Mutex` を使う。`utils.WithLocker` を呼ばないこと。

**根拠 (v0.6.0 で改めた)**: 既定の排他は、**2 者の同時取得を DPF-API の重複の拒否によって
機械的に防ぐ。この拒否は編集者に依らないため、ユーザ (アクセストークン) をまたいで効く**
(§2.3)。外部の仕組み (etcd など) に替えると、その仕組みを使うプログラム同士でしか防げなく
なる。別のクラスタ・別の DPF 連携ツールが同じゾーンを触る構成では、既定の排他のほうが
防げる範囲が広い。

**経緯**: v0.5.0 の時点では「別ユーザ (管理画面を含む) からの編集も DPF-API が拒否する」
ことを根拠としていた。**v0.6.0 ではどちらの方式も保持中の他ユーザの編集を止められない**
ため、根拠を同時取得の防止に置き直した。結論は変わらない。

本サービスは DNS という到達性の根幹を書き換える。排他の効き方が狭まることは、
憲章 原則 IV (DNS 変更の安全性) に対する後退である。分散ロックの基盤を別途運用する
利点は、本サービスの規模 (1 チャレンジあたり 1 ゾーン、同時数件) では生じない。

**帰結**: `utils/lockertest` は使わない (自作の `Locker` を持たないため)。
差し替えを禁止することを `internal/dpf` の境界で担保する。

### D-17: テストと CI の ACME サーバ

**決定**: 証明書の取得まで確かめる e2e は **Let's Encrypt のステージング環境**を用いる。
接続先は環境変数で与え、未設定時はステージング環境とする。テストと CI の設定を許可リスト
(ステージング環境のみ) と本番環境の一覧の双方で検査し、許可リスト外を CI で拒否する
(plan.md の Technical Context)。

**根拠**: 憲章 v3.2.0「ACME サーバの利用」は、本プロジェクトのテストと CI で本番環境の
ACME サーバを用いることを禁じる。本番環境の証明書は Certificate Transparency のログで
公開され、検証用ゾーンの名前が残る。発行数の制限に CI が達すると本番の運用に波及する。

**比較した案**:

| 案 | 評価 |
|---|---|
| **Let's Encrypt のステージング環境 (採用)** | 実際の DNS01 の検証 (公開 DNS を引く) を行う。検証用ゾーンは DPF の権威サーバで公開されるため成立する。発行数の制限は本番より緩い |
| テスト用の ACME サーバを CI 内に立てる (Pebble など) | 外部への依存が無く速い。ただし検証が CI 内の DNS を引くため、DPF に置いた TXT が**公開 DNS から見えること**を確かめられない。本サービスの e2e の目的 (DPF への反映の確認) に合わない。単体に近い結合テストでは使ってよい |
| 本番環境 | **憲章が禁じる** |

**許可リストを持つ理由**: 本番環境の一覧だけで拒否すると、一覧に無い認証局の本番環境を
見落とす。原則 VI (Default-Deny) に従い、許可したものだけを通す。本番環境の一覧は憲章が
「閉じた集合として plan に列挙すること」を求めるために持ち、拒否の理由をログに示すのに用いる。

**対象の範囲**: 本プロジェクトのテストと CI に限る。利用者向けの導入例 (README・quickstart の
ClusterIssuer の例) が本番環境を指すことは本来の用途であり、検査の対象にしない。

### D-18: 変更するゾーンは `ResolvedZone` と一致するゾーンに限る

**決定**: cert-manager が渡す `ResolvedZone` と一致する DPF のゾーンを変更する。
`utils.GetZoneFromName(ctx, cz, ResolvedZone, false)` で取得し、**返ったゾーンの名前が
`ResolvedZone` と正規化名で一致することを確かめる。**一致しなければ失敗させる。
あわせて `ResolvedFQDN` が `ResolvedZone` の配下にあることを `dns.IsSubDomain` で確かめる。

**根拠**: `ResolvedZone` は cert-manager が `ResolvedFQDN` から SOA を探索して求めた、
**実際に委任されているゾーン**である。ACME サーバは公開 DNS を引くため、書いたレコードが
見えるのはこのゾーンに書いた場合に限る。

| DPF の状況 | longest match (旧) | 採用した方式 |
|---|---|---|
| `ResolvedZone` のゾーンがある | 選ばれる | **選ぶ** |
| チャレンジ対象の FQDN と longest match するのが `ResolvedZone` の子ゾーン (委任が繋がっていない) | **子ゾーンが選ばれ、書いても公開 DNS から見えない** | 子ゾーンを選ばない |
| `ResolvedZone` が無く、親ゾーンだけがある | **親ゾーンが選ばれ、書いても委任先から見えない** | 失敗させる |

**経緯 (訂正)**: 当初は「DPF に登録されたゾーンと SOA 探索の結果が一致しない場合がある」
として `ResolvedZone` を参考値にとどめ、longest match を正としていた。**誤りであった。**
一致しない場合とは委任が繋がっていない場合であり、そのとき DPF 側のゾーンに書いても
検証は成立しない。

**dpf-go の関数**: `GetZoneFromZonename` / `GetZoneIDFromZonename` も内部は
`GetZoneFromName` の longest match であり、名前に完全一致するゾーンが無ければ親ゾーンを返す。
**完全一致で引く関数は無い**ため、本サービスが結果を確かめる。

**DPF が親ゾーンへの書き込みを拒否しないこと** (利用者確認): DPF に子ゾーンが登録されて
いても、**親ゾーンに子への NS レコードが無ければ**、親ゾーンへ子ゾーン配下の名前のレコードを
作ることを DPF は拒否しない。一方、**親ゾーンに子への NS レコードがあれば委任が繋がって
おり、SOA の探索は子ゾーンに到達するため、`ResolvedZone` は子ゾーンの名前になる。**
したがって `ResolvedZone` と一致するゾーンへの書き込みが、委任の有無によって拒否される
経路は無い。実環境での確認は要さない。

### D-20: テレメトリの構成 (US3)

**決定**: OpenTelemetry の SDK を用い、次のとおり構成する。

| 項目 | 決定 |
|---|---|
| メトリクス | 1 つの `MeterProvider` に、Prometheus 形式の reader (`/metrics`) と OTLP の reader (有効な場合) を付ける。同じ計測を読み手ごとに出力するため、両形式は同一の計測値を表す。計測は `dpf_webhook.challenge.requests` (要求) と `dpf_webhook.dns.record_changes` (ゾーンへの反映を要した変更操作)。属性は `action` と `result` に限る |
| トレース | 要求の span は solver が要求を受け取った時点に置く。`Present` / `CleanUp` には cert-manager の要求の context が渡されないためである。DPF の呼び出しの span はその子とし、1 つのトレースになる |
| 大域のトレーサ | **設定しない。**dpf-go は大域のトレーサで HTTP の呼び出しごとに span を作り、属性 `url.full` に問い合わせ文字列 (ゾーン名・レコード名を含む) を載せる。FR-092 に反するため、dpf-go の span は記録させない。本サービスのトレーサは context で DPF の境界へ渡す |
| 要求・応答の記録 | `internal/dpf` の共通の RoundTripper で行う。dpf-go はその外側で Authorization ヘッダを付けるため、ヘッダは記録せず、その値が本文に現れれば伏せる。エラー応答の本文は伏せたものに置き換えて上位へ返す。一括置換の本文は総数のみとし、差分は `Apply` が記録する |
| ロックの記録 | dpf-go に取得・解放の通知が無く、ロックの実装も差し替えない (D-16) ため、`Apply` の編集関数が呼ばれた時点 (保持中) と `Apply` から戻った時点で記録する |
| cert-manager へ返すエラー | cert-manager は solver が返したエラーの文字列を webhook の HTTP 応答 (`Status.Message`) に載せる。DPF のエラー応答の本文と送った要求の内容 (`ErrAPI` / `ErrUnavailable` の詳細) を除いたものを返し、全文はログに残す (FR-088b) |
| OTLP | 標準の環境変数 (`OTEL_EXPORTER_OTLP_ENDPOINT` / `_PROTOCOL` と信号ごとの指定) で与える。送出先が設定された信号のみ有効にする。方式は `grpc` と `http/protobuf` (省略時) で、それ以外は起動を中止する。TLS の検証は exporter の既定 (有効) に従う。送出の失敗は標準出力のみへ出すロガーに記録する |

**根拠**: 憲章 原則 V と FR-088〜092。Prometheus と OTLP の計測を別々に数えると、両者が
食い違う余地が生じる。
