# Feature Specification: DPF DNS01 Challenge Solver

**Feature Branch**: `feature/create-certmanager-webhook-server`

**Created**: 2026-09-18

**Status**: Draft

**Input**: User description: "APIService でリクエストを受ける WebHook サーバを作成します。フレームワークとしては、github.com/cert-manager/cert-manager/pkg/acme/webhook/cmd を使用し、DPF 固有の実装は webhook.Solver を実装することで実装することとします。また、Issuer / ClusterIssuer の config については、endpoint、tokenSecretRef (name / key / namespace)、domainFilters を持つスキーマとします。domainFilters に書かれたゾーンと一致したときのみ更新可能とし、glob で一致させます。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - ClusterIssuer でクラスタ全体の証明書を取得する (Priority: P1)

クラスタ管理者が、IIJ DNSプラットフォームサービス (DPF) で管理しているドメインに対して、
クラスタ内のどの namespace からでも証明書を発行できるようにしたい。管理者は DPF の
アクセストークンを Secret として 1 つ置き、ClusterIssuer を 1 つ作れば、あとは各利用者が
Certificate を作るだけで証明書が手に入る。

**Why this priority**: これが本機能の中核であり、単独で成立する最小の価値。これだけ動けば
「cert-manager で DPF のドメインの証明書が取れる」という目的は達成される。

**Independent Test**: ClusterIssuer と DPF アクセストークンの Secret を用意し、
DPF 管理下のドメインに対する Certificate を作成する。証明書が Ready になることで検証できる。

**Acceptance Scenarios**:

1. **Given** DPF 管理下のゾーン `example.com` と、webhook Pod と同じ namespace に
   `dpf-token` Secret がある状態で、**When** 管理者が `example.com` を含む Certificate を
   ClusterIssuer 経由で作成する、**Then** DNS01 チャレンジ用の TXT レコードが DPF に
   作成され、証明書が発行される。使用済みの RDATA とラベルは、期限を過ぎたのちの
   同一の名前に対する操作で回収される。
2. **Given** ClusterIssuer の config で `tokenSecretRef.namespace` が指定されている状態で、
   **When** チャレンジが実行される、**Then** 指定された namespace の Secret からトークンが
   読み出される。
3. **Given** ClusterIssuer の config で `tokenSecretRef.namespace` が省略されている状態で、
   **When** チャレンジが実行される、**Then** webhook Pod 自身が動作している namespace の
   Secret からトークンが読み出される。
4. **Given** ワイルドカード名 `*.example.com` を含む Certificate、**When** チャレンジが
   実行される、**Then** `_acme-challenge.example.com` に対する TXT レコードが作成される。
5. **Given** チャレンジが処理される、**When** DPF のゾーン変更履歴を確認する、
   **Then** 本サービスによる変更であることと、設定されたロックオーナーが Description から読み取れる。
6. **Given** 他のソフトウェアが対象ゾーンのロックを保持している状態で、**When** チャレンジが
   実行される、**Then** 本サービスはそのロックを奪わず、解放を待ってから変更を適用する。
7. **Given** config の `domainFilters` に `example.jp` が含まれている状態で、**When**
   `example.jp` を対象とするチャレンジが実行される、**Then** レコードが変更される。
8. **Given** config の `domainFilters` が空である状態で、**When** チャレンジが実行される、
   **Then** レコードは変更されず、変更可能なゾーンが存在しない旨がログに記録される。
9. **Given** config の `domainFilters` に `*.example.jp` のみが含まれている状態で、
   **When** `sub.sub.example.jp` を対象とするチャレンジが実行される、**Then**
   レコードが変更される。
10. **Given** `_acme-challenge.example.jp` が `hoge.delegated.example` へ CNAME で
    委譲され、`domainFilters` に `delegated.example` が含まれている状態で、**When**
    チャレンジが実行される、**Then** `hoge.delegated.example` の TXT レコードが変更される。
11. **Given** 同じ構成で `domainFilters` に `example.jp` のみが含まれている状態で、
    **When** チャレンジが実行される、**Then** 委譲先のゾーンが許可されていないため
    要求は失敗し、レコードは変更されない。

### User Story 2 - namespace に閉じた Issuer でテナントごとに証明書を取得する (Priority: P2)

個々のチームが、自分の namespace に自分の DPF アクセストークンを置き、他チームの
認証情報に触れることなく証明書を取得できるようにしたい。チームごとに DPF の契約や
権限が異なる場合に必要になる。

**Why this priority**: P1 だけでもクラスタは機能するが、マルチテナントのクラスタでは
「全員が同じトークンを共有する」ことが許されない。テナント分離はその前提を満たすための
独立した価値。

**Independent Test**: 2 つの namespace にそれぞれ別のトークン Secret と Issuer を置き、
各 namespace の Certificate がそれぞれのトークンで処理されることを確認する。
一方の namespace から他方の Secret に到達できないことも確認する。

**Acceptance Scenarios**:

1. **Given** namespace `team-a` に `dpf-token` Secret と Issuer がある状態で、
   **When** `team-a` の Certificate が処理される、**Then** `team-a` の Secret から
   トークンが読み出される。
2. **Given** namespace `team-a` の Issuer の config が `tokenSecretRef.namespace: team-b` を
   指定している状態で、**When** チャレンジが実行される、**Then** 要求は失敗し、
   `team-b` の Secret は読み出されない。
3. **Given** namespace `team-a` に Secret が存在しない状態で、**When** チャレンジが
   実行される、**Then** 要求は恒久的な失敗として返され、再試行が繰り返されない。

### User Story 3 - 失敗したチャレンジの原因を切り分ける (Priority: P3)

証明書が発行されないとき、管理者が Pod のログだけを見て、原因が設定なのか、
トークンなのか、DPF 側なのかを判断できるようにしたい。

**Why this priority**: 発行が成功する経路 (P1/P2) が先に必要だが、無人で繰り返し動作する
コンポーネントでは、失敗したときに原因が分からないことが運用上の最大のコストになる。

**Independent Test**: 誤ったトークン、存在しないゾーン、不正な config をそれぞれ与え、
ログからどれが原因かを判別できることを確認する。

**Acceptance Scenarios**:

1. **Given** 無効なトークンが設定されている状態で、**When** チャレンジが実行される、
   **Then** DPF が返したエラー応答が全文ログに記録され、問い合わせ用の識別子が失われない。
2. **Given** DPF に存在しないドメインの Certificate、**When** チャレンジが実行される、
   **Then** 「委任されたゾーン (`ResolvedZone`) が DPF に見つからない」旨と、`ResolvedZone`
   および対象 FQDN がログに記録される。
3. **Given** いずれの失敗経路でも、**When** ログを確認する、**Then** トークンの値が
   ログ・エラーメッセージ・メトリクス・トレースのいずれにも現れない。

### Edge Cases

- **同一 FQDN に複数のチャレンジ値が必要な場合** (SAN 証明書、`example.com` と
  `*.example.com` の同時取得): 同一のチャレンジ名に複数の TXT 値が並ぶ。
  一方の後片付けが他方の値を消してはならない。
- **`_acme-challenge` が CNAME で委譲されている場合**: cert-manager が CNAME を辿り、
  委譲先の FQDN が書き込み対象として、委譲先の FQDN から求めたゾーンが `ResolvedZone` として
  渡される。本サービスは渡された FQDN をそのまま用い、`ResolvedZone` と一致するゾーンに対して
  `domainFilters` を判定する。
- **委譲先が `domainFilters` に一致しないゾーンにある場合**: 委譲元のゾーンが許可されていても、
  要求は失敗し、レコードは変更されない。
- **複数のドメインが同一の委譲先を共有している場合** (acme-dns 的な構成): 同一の TXT 名に
  異なる証明書のチャレンジ値が同時に並ぶ。後片付けはいずれの値も消さず、期限を過ぎた
  値だけが次の操作で回収される。
- **複数のクラスタが同一の ACME アカウントで同一の名前の証明書を取得する場合**:
  同一のチャレンジコードを受け取ることがある。**後片付けは RDATA を削除しない**ため、
  一方の後片付けが他方の検証中の RDATA を消すことがない。
- **同一の配備から、同一のチャレンジコードを持つ 2 つのチャレンジが同時に発生した場合**:
  同上。削除する動作がないため区別を要しない。
- **後片付けが同一のチャレンジに対して 2 回呼ばれた場合**: 期限切れの回収のみであり、
  2 回目は何も起きない。
- **呼び出し元がタイムアウトしたのち処理が成功し、再試行が来た場合**: 提示は RDATA を
  重複させず期限のみを更新する。後片付けは回収のみであり、何も起きない。
- **取り残された後片付けが、後続の提示のあとに実行された場合**: 後片付けは削除を
  行わないため、後続の提示を打ち消さない。
- **望む最終状態が既に成立している場合** (提示で RDATA とラベルが揃い、ラベルの残りが
  閾値以上 / 後片付けで回収すべきものが無い): **ゾーンへの変更を一切行わない。**
  排他の取得も反映も行わない。成功として返す。
- **再試行が重なった場合**: 元の提示が設定した期限の残りが閾値以上であるため、
  いずれの再試行も変更を行わない。同一ゾーンへの直列の待ち行列を作らない。
- **RDATA は存在するが対応するラベルが無い場合**: ラベルを追加する。
  ラベルを持たない RDATA は回収されず永久に残るため、この場合は変更を行う。
- **実行が途中で消滅した場合**: 期限を過ぎたのち、次に同一の名前を操作したときに
  ラベルと RDATA が取り除かれる。
- **ラベルの件数が上限 10 に達した場合**: 要求を失敗させ、ログに記録する。
  他者のラベルも本サービスの記録も追い出さない。
- **チャレンジレコードに本サービス以外のラベルが付いている場合**: それらは追加時も
  削除時も維持される。枠は共有されるため、その分だけ収容できる記録が減る。

- **委譲先が DPF の管理外にある場合**: `ResolvedZone` と一致するゾーンが DPF に見つからず、
  要求は失敗する。
- **Present が重複して呼ばれた場合**: 同じ FQDN と同じチャレンジコードで再度呼ばれても、
  RDATA が二重にならず、最終状態が変わらない。
- **同名の TXT レコードに本サービス以外が置いた RDATA がある場合** (SPF、ドメイン所有確認など):
  それらの RDATA は追記時も削除時も維持される。
- **後片付けで RDATA が 1 つも残らなくなる場合**: レコードごと削除され、RDATA が空の
  レコードは残らない。ラベルもレコードとともに失われる。
- **後片付けで他の RDATA が残る場合**: レコードは残り、残った RDATA と TTL が維持される。
- **CleanUp が Present なしで呼ばれた場合**、および **削除対象が既に存在しない場合**:
  失敗とせず、成功として扱う。
- **同一ゾーンに対する同時変更**: 複数のチャレンジが同じゾーンを同時に書き換えようとした
  場合、互いの変更を取り消さない。
- **他のソフトウェアがゾーンロックを保持している場合**: 本サービスはそのロックを奪わず、
  上限を定めて待機する。上限に達した場合は一時的な失敗として返す。
- **本サービスが別クラスタに同時に配備されている場合**: ロックオーナーによって、どちらの配備が
  ロックを保持しているかを区別できる。
- **ロックを保持したまま本サービスが異常終了した場合**: ゾーンがロックされたまま残り続けない。
- **1 回の処理が要求のタイムアウト (60 秒) を越えた場合**: これは**通常起こりうる経路として
  扱う。** 呼び出し元にはタイムアウトが返るが、本サービスの処理は操作期限まで続き、
  完了しうる。cert-manager の再試行は、完了後であれば望む最終状態が成立しているため
  ゾーンへの変更を行わずに成功する。
- **先の処理がまだ走っている間に再試行が来た場合**: 再試行はロックを奪わずに待つ。
  取得できた時点で読み直した状態が望む最終状態であれば、反映を行わずに成功する。
  操作期限までに取得できなければ一時的な失敗として返し、次の再試行に委ねる。
- **操作期限に達した場合**: 操作期限を越えて DPF への書き込みは行われない。ロックの解放は
  期限切れの context のため失敗しうるが、TTL の満了で失効する。
  cert-manager の再試行によって回復する。
- **反映は完了したが、ロックの解放だけが失敗した場合**: 要求の失敗として返す。
  ロックは TTL の満了で失効し、再試行は望む最終状態が成立しているため変更を行わずに成功する。
- **呼び出し元がタイムアウトしたのち、本サービスの処理が成功した場合**: 再試行は
  同一のキーの記録を見つけ、残りが閾値以上であれば何も変更しない。記録も RDATA も増えない。
  `CleanUp` の場合は回収のみであり、何も起きない。
- **取り残された `CleanUp` が、後続の `Present` のあとに実行された場合**: 後片付けは
  削除を行わないため、後続の記録を消さない。
- **変更の適用前に中断した場合**: live なゾーンは無変更のまま残る。
- **変更の適用中にロックを奪われた場合**: 書き込みを行わずに失敗する。
- **ゾーンに本サービスと無関係なレコードがある場合**: それらは RDATA・TTL・ラベル・
  コメントのいずれも変更されない。
- **排他に参加しない変更者が編集中の状態にしている場合**: その未反映の編集は
  本サービスの適用によって失われる。**他ユーザ・管理画面からの編集は、ロックの保持中も
  止められない。** 排他に参加しない変更者を防ぐ手段はない。
- **同じゾーンを、旧版 (v0.5.0 以前) の `dpf-go` を用いるプログラムが操作する場合**:
  互いのロックを認識できず、排他が成立しない。本サービスはこれを検出できない。
  同じゾーンを触るプログラムはまとめて更新する必要がある。
- **対象ゾーンのラベルが既に上限に達している場合**: ロックを取得できず、要求を失敗させる。
  ロックはゾーンのラベルを 1 つ恒久的に消費するため、利用者が付けられるゾーンのラベルは
  9 個までになる。
- **ロックオーナーがちょうど 32 文字の場合**: 受け付ける。Description は 49 文字となり、
  DPF の上限に収まる。切り詰めは発生しない。
- **ロックオーナーが 33 文字以上、または許されない文字を含む値で設定された場合**:
  起動時に検出され、異常終了する。切り詰めて起動を続行しない。
- **config で未知のフィールドが指定された場合**: 黙って無視せず、要求を失敗させる。
- **`domainFilters` が空または未指定の場合**: いかなるゾーンも変更しない。
- **`domainFilters` に `*` のみが書かれた場合**: トークンが到達できるすべてのゾーンが対象となる。
  既定の拒否を緩める設定であるため、警告がログに記録される (FR-023a)。
- **`*.example.jp` のみが書かれ、対象ゾーンが `example.jp` 自身の場合**: 一致せず、
  要求は失敗する。頂点も許可するには `example.jp` の併記が必要。
- **`*example.jp` のようにラベルの一部が `*` のパターンが書かれた場合**: 受け付けず、
  要求を失敗させる。`evilexample.jp` への一致を防ぐため。
- **ゾーン名とパターンで大文字小文字や末尾ドットが異なる場合**: 判定結果が変わらない。
- **`domainFilters` に一致しないゾーンが対象となった場合**: レコードを一切変更せずに失敗する。
- **`tokenSecretRef.namespace` が namespace 限定 Issuer で指定された場合**:
  その値を採用せず、また `ResourceNamespace` へ読み替えもせず、要求を失敗させる。
- **Secret は存在するが指定された key がない場合**、および **値が空の場合**:
  恒久的な失敗として扱う。
- **トークンが外部でローテーションされた場合**: 再起動なしに新しい値が使われる。
- **DPF が変更の反映に明示的な適用操作を要求する場合**: 適用が完了するまでを 1 つの
  操作として扱い、未適用のまま成功を返さない。
- **DPF への到達に失敗した場合**: 一時的な失敗として扱い、上限を定めた再試行を行う。
- **チャレンジ対象の FQDN と longest match する DPF のゾーンが、`ResolvedZone` ではない
  場合** (FQDN が `_acme-challenge.www.sub.example.com`、`ResolvedZone` が `example.com` で、
  DPF に `sub.example.com` もある): FQDN と longest match するのは `sub.example.com` だが、
  委任が繋がっていないため選ばない。`ResolvedZone` と一致する `example.com` を編集する。
- **`ResolvedZone` と一致するゾーンが DPF に無い場合** (DPF にはその親ゾーンだけがある場合を
  含む): 親ゾーンへ読み替えず、要求を失敗させる。親ゾーンに書いたレコードは、委任先の
  権威サーバから見えないため。

## Requirements *(mandatory)*

### Functional Requirements

#### solver の同一性と受け口

- **FR-001**: 本サービスは DNS01 solver として、グループ名 `acme.dns-platform.jp`、
  solver 名 `iij-dpf` で自身を識別できなければならない (MUST)。
- **FR-002**: 本サービスは Kubernetes の APIService として登録され、kube-apiserver の
  集約層を経由した要求のみを処理しなければならない (MUST)。集約層以外から到達した接続は
  クライアント証明書の検証に失敗し、要求に至ってはならない (MUST NOT)。

#### solver 設定 (Issuer / ClusterIssuer の config)

- **FR-003**: 本サービスは Issuer / ClusterIssuer の solver 設定として、次のフィールドを
  受け付けなければならない (MUST)。

  | フィールド | 必須 | 既定値 |
  |---|---|---|
  | `endpoint` | 任意 | `https://api.dns-platform.jp/dpf/v1` |
  | `tokenSecretRef.name` | 任意 | `dpf-token` |
  | `tokenSecretRef.key` | 任意 | `token` |
  | `tokenSecretRef.namespace` | 任意 | ClusterIssuer のときのみ有効。省略時は本 Pod の namespace |
  | `domainFilters` | 任意 | `[]` (空のとき、いかなるゾーンも変更しない) |

- **FR-004**: 設定に未知のフィールドが含まれる場合、要求を失敗させなければならない (MUST)。
  未知のフィールドを黙って無視してはならない (MUST NOT)。
- **FR-005**: 設定の解釈に失敗した場合、既定値へフォールバックして処理を続行しては
  ならない (MUST NOT)。

#### トークンの取得

- **FR-006**: 本サービスは DPF アクセストークンを Kubernetes の Secret から取得しなければ
  ならない (MUST)。取得元の namespace は、要求が ClusterIssuer 由来か namespace 限定の
  Issuer 由来かによって決まらなければならない (MUST)。

  | 要求の由来 | 読み取りを許す namespace |
  |---|---|
  | namespace 限定の Issuer | 当該要求の `ResourceNamespace` のみ |
  | ClusterIssuer | `tokenSecretRef.namespace`、省略時は本 Pod の namespace |

- **FR-007**: namespace 限定の Issuer 由来の要求において、`tokenSecretRef.namespace` が
  `ResourceNamespace` 以外を指している場合、要求を失敗させなければならない (MUST)。
  当該フィールドを無視して処理を続行してはならない (MUST NOT)。
- **FR-008**: 指定された Secret が存在しない、指定された key が存在しない、または値が
  空である場合、恒久的な失敗として扱い、再試行を繰り返してはならない (MUST NOT)。
- **FR-009**: Kubernetes API への到達に失敗した場合は一時的な失敗として扱い、上限を定めた
  再試行の対象としてよい (MAY)。上限のない再試行を行ってはならない (MUST NOT)。
- **FR-010**: 恒久的な失敗と一時的な失敗のいずれに分類したかをログに記録しなければ
  ならない (MUST)。
- **FR-011**: トークンが外部でローテーションされた場合、本サービスの再起動なしに新しい値が
  使われなければならない (MUST)。
- **FR-012**: トークンの値、およびトークンを含む Secret の内容を、ログ・エラーメッセージ・
  メトリクス・トレース・HTTP 応答本文のいずれにも出力してはならない (MUST NOT)。

#### ゾーンの特定

- **FR-013**: 本サービスが変更するゾーンは、cert-manager が渡す **`ResolvedZone`
  (書き込む FQDN から SOA を探索して求めた、実際に委任されているゾーン) と一致する
  DPF のゾーン**でなければならない (MUST)。
  - チャレンジ対象の FQDN と longest match する DPF のゾーンを選んではならない (MUST NOT)。
    それが `ResolvedZone` と異なる場合 (`ResolvedZone` の子ゾーンである場合)、そのゾーンは
    委任が繋がっておらず、書いたレコードが公開 DNS から見えない。
  - `ResolvedZone` と一致するゾーンが無い場合に、その親ゾーンへ読み替えてはならない
    (MUST NOT)。
  - cert-manager が CNAME を辿る構成では、`ResolvedZone` は委任先の名前に対して求められる。
    証明書の対象ドメインからゾーンを特定してはならない (MUST NOT)。
- **FR-014**: ゾーン名の一致の判定は、正規化名どうしの一致で行わなければならない (MUST)。
  あわせて、書き込む FQDN (`ResolvedFQDN`) が `ResolvedZone` の配下にあることを
  ラベル境界で確かめ、そうでなければ要求を失敗させなければならない (MUST)。
  文字列としての接尾辞一致で判定してはならない (MUST NOT)。
- **FR-015**: `ResolvedZone` と一致するゾーンが DPF に見つからない場合、要求を失敗させ
  なければならない (MUST)。`ResolvedZone` と対象 FQDN をログに記録しなければならない (MUST)。

#### 対象ゾーンの制限 (domainFilters)

- **FR-016**: 本サービスは、特定したゾーンが `domainFilters` のいずれかのパターンに
  一致する場合にのみ、そのゾーンを変更しなければならない (MUST)。一致しない場合は
  要求を失敗させ、いかなるレコードも変更してはならない (MUST NOT)。
- **FR-017**: 判定の対象は、**FR-013 で特定したゾーン (`ResolvedZone` と一致するゾーン)**
  でなければならない (MUST)。
  証明書の対象ドメイン、またはそれを含むゾーンに対して判定してはならない (MUST NOT)。
  CNAME による委譲を使う構成では、委譲先が別のゾーンに属する。委譲先のゾーンが
  `domainFilters` に一致しない場合、要求を失敗させなければならない (MUST)。
  委譲元のゾーンが許可されていることを理由に、委譲先への書き込みを許してはならない
  (MUST NOT)。
- **FR-018**: 一致の判定は、レコードを書き込む直前に行わなければならない (MUST)。
  ゾーンを特定した時点の判定結果を、後続の書き込みまで持ち回してはならない (MUST NOT)。
- **FR-019**: `domainFilters` が空または未指定の場合、いかなるゾーンも変更しては
  ならない (MUST NOT)。空を「すべてのゾーンを許可」と解釈してはならない (MUST NOT)。
  変更可能なゾーンが存在しない旨をログに記録しなければならない (MUST)。
- **FR-020**: パターンとして受け付ける形式は次の 3 つのみでなければならない (MUST)。

  | パターン | 意味 | 例: 一致するゾーン | 例: 一致しないゾーン |
  |---|---|---|---|
  | `*` | すべてのゾーン | 任意 | — |
  | `*.example.jp` | `example.jp` の配下にあるすべてのゾーン (深さを問わない) | `sub.example.jp`, `sub.sub.example.jp` | `example.jp`, `evilexample.jp`, `example.jp.attacker.test` |
  | `example.jp` | そのゾーンと完全一致するもの | `example.jp` | `sub.example.jp`, `evilexample.jp` |

- **FR-021**: `*.example.jp` は `example.jp` 自身に一致してはならない (MUST NOT)。
  ゾーンの頂点も許可する場合は、`example.jp` を併記しなければならない (MUST)。
- **FR-022**: 上記 3 形式以外のパターンを受け付けてはならない (MUST NOT)。
  `*` を含むパターンは、`*` 単独か、先頭ラベル全体が `*` である形 (`*.<ドメイン>`) の
  いずれかでなければならない (MUST)。`*example.jp` のようにラベルの一部が `*` である
  パターン、および `*` が先頭以外のラベルに現れるパターンを拒否しなければならない (MUST)。
- **FR-023**: 受け付けられない形式のパターンが指定された場合、要求を失敗させなければ
  ならない (MUST)。当該パターンを無視して残りのパターンで処理を続行してはならない
  (MUST NOT)。解釈できないパターンを「一致しない」として扱ってはならない (MUST NOT)。
- **FR-023a**: `domainFilters` に `*` (すべてのゾーン) が含まれる場合、既定の拒否を
  緩める設定であることを**警告としてログに記録しなければならない (MUST)。** 記録には
  当該の Issuer / ClusterIssuer を識別できる情報 (要求元の namespace と、ClusterIssuer 由来か
  どうか) を含める。`*.<ドメイン>` による配下の一括許可は、範囲が限定されるため対象としない。
- **FR-024**: `domainFilters` の一致の判定は、ドメイン名のラベル境界で行わなければならない
  (MUST)。文字列としての部分一致・接尾辞一致で判定してはならない (MUST NOT)。
  `*.<ドメイン>` の配下の判定はラベル単位の包含関係で行い、完全一致は正規化名どうしの一致で
  行う (FR-020〜022)。
- **FR-025**: 判定に先立ち、パターンとゾーン名の双方を正規化しなければならない (MUST)。
  大文字小文字の違い、および末尾ドットの有無によって判定結果が変わってはならない
  (MUST NOT)。

**注**: `domainFilters` は設定誤りに対する歯止めであり、テナント間の認可境界ではない。
namespace の利用者は自分の Issuer に `*` を書けるが、到達できるゾーンは自分の namespace に
置いたアクセストークンが許す範囲に限られる。認可の境界はトークンであり、
`domainFilters` はその内側でさらに範囲を狭めるためのものである。

#### チャレンジレコードの操作

*操作の単位*

- **FR-026**: TXT レコードの変更は、**レコードが保持する RDATA の集合に対する追加・削除**
  として行わなければならない (MUST)。レコード全体を置き換えてはならない (MUST NOT)。
  レコードを削除して作り直す形で変更を行ってはならない (MUST NOT)。
- **FR-027**: 変更は、現在の RDATA を読み出し、当該チャレンジの値を加除し、その結果を
  書き戻す形で行わなければならない (MUST)。読み出しから書き戻しまでを、対象ゾーンの
  ロックを保持した状態で行わなければならない (MUST)。ロックの外で読み出した RDATA を
  もとに書き戻してはならない (MUST NOT)。

*提示 (Present)*

- **FR-028**: 対象 FQDN の TXT レコードに、指定されたチャレンジコードが RDATA として
  存在する状態にしなければならない (MUST)。
- **FR-029**: 同名の TXT レコードが既に存在する場合、**既存の RDATA をすべて維持したまま**、
  チャレンジコードを RDATA として追記しなければならない (MUST)。既存の RDATA を
  削除・変更してはならない (MUST NOT)。
- **FR-030**: 指定されたチャレンジコードが既に RDATA として存在する場合、重複して
  追記してはならない (MUST NOT)。
- **FR-031**: 同名の TXT レコードが存在しない場合は、新たに作成しなければならない (MUST)。
- **FR-032**: 既存のレコードに追記する場合、そのレコードの TTL を変更してはならない
  (MUST NOT)。TTL を定めるのは、レコードを新たに作成する場合に限る (MUST)。

*削除 (期限切れの回収)*

- **FR-033**: 削除してよいのは、**期限切れとして回収の対象になった RDATA のみ**である
  (MUST)。同名のレコードが持つ他の RDATA を削除・変更してはならない (MUST NOT)。
  回収の規則は「使用済みレコードの回収 (expire)」節に従う。
- **FR-034**: 削除後に RDATA が 1 つ以上残る場合、レコードを残し、残った RDATA を
  維持しなければならない (MUST)。レコードごと削除してはならない (MUST NOT)。
- **FR-035**: 削除後に RDATA が 1 つも残らない場合、レコードを削除しなければならない
  (MUST)。RDATA が空のレコードを残してはならない (MUST NOT)。
- **FR-036**: 削除にあたり、他の RDATA の TTL および並び順に依存した処理を行っては
  ならない (MUST NOT)。削除対象は値の一致によって特定しなければならない (MUST)。
- **FR-037**: すべての適用操作は冪等でなければならない (MUST)。同一の操作を再実行しても
  最終状態が変わらず、追加の破壊的副作用を生んではならない (MUST NOT)。
  期限の値のみが更新されることは、この冪等性を損なわない。
- **FR-038**: 削除対象が既に存在しない場合、および Present を伴わない CleanUp が呼ばれた
  場合、失敗とせず成功として扱わなければならない (MUST)。
- **FR-039**: TXT 以外の種別のレコードを変更・削除してはならない (MUST NOT)。
- **FR-040**: 書き込み対象のレコード名を `_acme-challenge` で始まる名前に限定しては
  ならない (MUST NOT)。cert-manager が CNAME を辿った結果、委譲先の任意の名前
  (例: `_acme-challenge.example.jp` の CNAME 先である `hoge.delegated.example`) が
  書き込み対象となりうるため。
- **FR-041**: 書き込み対象のレコード名は、cert-manager から与えられた FQDN を用いなければ
  ならない (MUST)。本サービスが独自に名前を組み立ててはならない (MUST NOT)。

- **FR-042**: DPF が変更の反映に明示的な適用操作を要求する場合、その完了までを 1 つの
  操作として扱わなければならない (MUST)。未適用の変更を残したまま成功を返しては
  ならない (MUST NOT)。
- **FR-043**: 変更適用中にエラーが発生した場合、部分的に成功した状態を成功として
  返してはならない (MUST NOT)。
- **FR-044**: 同一ゾーンに対する複数の変更が同時に発生した場合、互いの変更を取り消しては
  ならない (MUST NOT)。直列化の手段は「ゾーンロックと変更の記録」の規定 (特に FR-052) に
  従う (MUST)。

**注**: 本サービスが変更しうる範囲は、レコード名ではなく次の 3 点で閉じている。
(1) 対象ゾーンが `domainFilters` に一致すること、(2) 種別が TXT であること、
(3) 当該チャレンジのチャレンジコードに対応する RDATA と、期限切れとして回収の対象に
なった RDATA、およびそれらに対応するラベルのみを追加・削除すること
(「使用済みレコードの回収 (expire)」節を参照)。
レコード名を縛らないのは、CNAME による委譲を使う構成を妨げないためである。

#### ゾーンロックと変更の記録

- **FR-045**: ゾーンへの変更は、DPF のゾーンロックを取得してから行わなければならない (MUST)。
  ロックを取得せずに変更を適用してはならない (MUST NOT)。
- **FR-046**: ロックの取得・変更・適用・ロックの解放を 1 つの操作として扱わなければ
  ならない (MUST)。変更の適用が完了する前にロックを解放してはならない (MUST NOT)。
- **FR-047**: ロックオーナーは設定可能でなければならない (MUST)。本サービスの名称のみからなる
  固定値をロックオーナーとしてはならない (MUST NOT)。複数のクラスタが同一ゾーンを更新する場合に、
  どのクラスタが保持しているロックかを区別できなければならない (MUST)。
- **FR-048**: ロックオーナーは 1 文字以上 32 文字以下で、英数字と `.` `-` `_` のみから
  なる値でなければならない (MUST)。これを満たさない値を受け付けてはならない (MUST NOT)。
  長さの上限は `dpf-go` のロックが保持者として受け付ける上限である (保持者はゾーンの
  ラベルの値に、奪ってよい時刻とともに詰めて格納される)。文字種はラベルの値の共通ルールに
  よる。この上限のもとで FR-064 の Description は 80 文字以内に収まる。
- **FR-049**: ロックオーナーは本サービスの配備単位の設定として与えなければならない (MUST)。
  Issuer / ClusterIssuer の solver 設定から指定できるようにしてはならない (MUST NOT)。
  ロックオーナーは「どの配備がゾーンを掴んでいるか」を表すものであり、要求ごとに変わってよい
  値ではない。
- **FR-050**: ロックオーナーが未設定のまま起動してはならない (MUST NOT)。起動時に設定の充足を
  検証し、不足していれば異常終了しなければならない (MUST)。区別可能な既定値を本サービスが
  推測してはならない (MUST NOT)。
- **FR-051**: 期限内の他者のロックを奪ってはならない (MUST NOT)。期限を過ぎたロックの
  奪取は許容する (MAY)。保持者が消滅した場合にゾーンが恒久的にロックされることを
  防ぐために必要である。
- **FR-052**: ゾーンロックは、同一のアクセストークンを用いる複数の実行の間でも
  排他を成立させなければならない (MUST)。同一の配備から同時に発生した変更が、
  互いの変更を失わせてはならない (MUST NOT)。
- **FR-053**: 変更の適用中にロックを他者へ奪われた場合、書き込みを行ってはならない
  (MUST NOT)。保護が切れたことを検知できない設計にしてはならない (MUST NOT)。
- **FR-054**: ロックを取得できない場合、上限を定めて待機・再試行しなければならない (MUST)。
  待機の上限は操作期限とする (MUST)。試行の間隔の既定値は data-model.md の配備単位の設定に定める。
  上限に達した場合は一時的な失敗として返さなければならない (MUST)。上限のない待機を
  行ってはならない (MUST NOT)。
- **FR-055**: 変更の適用によって、本サービスが対象としていないレコードを変更・削除しては
  ならない (MUST NOT)。RDATA・TTL・ラベル・コメントのいずれも、元のまま維持しなければ
  ならない (MUST)。適用の手段がゾーン全体を対象とする場合も、この要件は変わらない。
- **FR-056**: ゾーンの頂点の SOA レコードおよび NS レコードを変更してはならない
  (MUST NOT)。
- **FR-057**: 操作全体に期限 (以下「**操作期限**」) を設けなければならない (MUST)。
  操作期限は設定可能とし、
  **要求のタイムアウト (60 秒) より長い**既定値としなければならない (MUST)。
  1 回の処理は 60 秒を越えうる。呼び出し元へタイムアウトが返ったのちも処理を完了まで
  進め、再試行が望む最終状態を見つけて成功する (FR-083) ことで収束させる。
  操作期限の役割は、取り残された処理が走り続ける時間に上限を設けることである。
  `Present` および `CleanUp` には呼び出しの context が渡されないため、呼び出しの中断を
  観測できない。本サービス自身が操作期限を持つほかない。
- **FR-057a**: 操作期限は、受けた要求の context から派生させてはならない (MUST NOT)。
  呼び出し元のタイムアウトによって処理が打ち切られると、完了しない処理が再試行のたびに
  繰り返され、収束しなくなるため。
- **FR-058**: 操作期限は DPF への呼び出しまで伝播させ、**操作期限を越えて DPF への書き込みを
  行ってはならない (MUST NOT)。** 取り残された処理が際限なく走り続ける経路を作らないため。
- **FR-059**: 操作期限に達した場合、ロックの解放を試みなければならない (MUST)。ただし
  **解放は失敗しうる。** 解放の呼び出しは期限切れの context を用いるため、操作期限が原因で
  失敗する。この場合はロックの TTL による失効に委ねてよい (MAY)。
  解放の成否に処理の正しさを依存させてはならない (MUST NOT)。
  **反映が完了したのちに解放だけが失敗した場合も、要求の失敗として返さなければならない
  (MUST)。** 反映の失敗と解放の失敗を区別しない。再試行は望む最終状態を見つけて
  変更を行わずに成功するため (FR-083)、失敗として返しても害がない。
- **FR-060**: ロックの TTL は、1 回の操作を覆う長さとしなければならない (MUST)。
  中断した保持者が他の実行をブロックする時間を不必要に長くしてはならない (MUST NOT)。
  操作期限に達した場合の解放がこの失効に委ねられるため、**TTL の長さがそのまま他の実行を
  ブロックしうる時間になる。** 既定値は data-model.md の配備単位の設定に定める (2 分)。
- **FR-061**: ロックの解放の完了 (書き込みの確定) を待つ必要はない。`dpf-go` の解放は
  書き込みの確定を待たずに返る。解放が失敗した場合もロックは TTL の満了によって失効する
  ため、本サービスが確定を待つ処理を加えてはならない (MUST NOT)。
- **FR-062**: (FR-060 に統合) 解放に失敗しても他の実行が不必要に長く待たされないことは、
  FR-060 の TTL の要件によって満たす。
- **FR-063**: 変更の途中でエラーが発生した場合も、取得したロックを解放しなければ
  ならない (MUST)。本サービスの異常終了によって、ゾーンがロックされたまま残り続ける状態を
  作ってはならない (MUST NOT)。
- **FR-064**: ゾーンの変更を適用する際、次の形式の Description を付与しなければ
  ならない (MUST)。

  ```
  by cert-manager(<ロックオーナー>)
  ```

  - 固定部 `by cert-manager()` は 17 文字である。ロックオーナーの上限 32 文字 (FR-048) を
    加えても 49 文字であり、DPF の Description の上限 80 文字に収まる。
  - この形式以外の Description を付与してはならない (MUST NOT)。Description を
    切り詰めてはならない (MUST NOT)。FR-048 の上限が守られている限り、切り詰めは発生しない。
  - Description にアクセストークン、ゾーン名、レコード名、レコード値を含めては
    ならない (MUST NOT)。
- **FR-065**: ロックの取得・解放、および適用した Description をログに記録しなければ
  ならない (MUST)。

#### 使用済みレコードの回収 (expire)

- **FR-066**: チャレンジ用の RDATA は、**期限 (expire) に基づいて回収**しなければならない
  (MUST)。本仕様で単に「期限」と書く場合はこの回収の期限を指し、FR-057 の操作期限とは
  区別する。後片付けの時点で削除してはならない (MUST NOT)。
  複数の実行が同一のチャレンジコードを同時に必要とする場合があり、一方の後片付けが
  他方の必要とする RDATA を消してはならないため。

*期限の記録*

- **FR-067**: チャレンジレコードのラベルに、RDATA ごとの期限を記録しなければ
  ならない (MUST)。記録のために別のレコードを作ってはならない (MUST NOT)。
- **FR-068**: ラベルは 1 つのチャレンジコードにつき 1 つとしなければならない (MUST)。
  キーは対象のチャレンジコードを識別し、値は期限を表さなければならない (MUST)。
- **FR-069**: キーには、本サービスの記録であることを判別できる接頭辞を含めなければ
  ならない (MUST)。接頭辞が一致しないラベルを、追加時も削除時も維持しなければ
  ならない (MUST)。ラベルの集合全体を置き換えてはならない (MUST NOT)。
- **FR-070**: 記録に**保持者を識別する値を含めてはならない (MUST NOT)。**
  期限による回収は保持者を区別しないため、識別は不要である。
- **FR-071**: 記録にアクセストークンを含めてはならない (MUST NOT)。
  チャレンジコードそのものを復元できる表現を用いてはならない (MUST NOT)。

*回収 (掃除)*

- **FR-072**: `Present` と `CleanUp` の双方において、**処理の最初に期限切れの回収を
  行わなければならない (MUST)。** 期限を過ぎたラベルと、それに対応する RDATA を
  取り除かなければならない (MUST)。
- **FR-073**: 回収の対象は、**RDATA の値から導いた識別値が、期限切れのラベルのキーと
  一致するもの**に限らなければならない (MUST)。識別値はダイジェストでありチャレンジコードを
  復元できないため、レコード内の各 RDATA から識別値を計算して突き合わせること (MUST)。
- **FR-074**: 対応するラベルを持たない RDATA を削除してはならない (MUST NOT)。
  本サービス以外が置いた値である可能性があるため。
- **FR-075**: 期限切れのラベルは、対応する RDATA の有無によらず取り除かなければ
  ならない (MUST)。
- **FR-076**: 回収のために常時動く処理を設けてはならない (MUST NOT)。
  回収は `Present` と `CleanUp` の内部でのみ行う。

*提示 (Present)*

- **FR-077**: 回収を行ったのち、FR-028〜FR-030 に従って当該チャレンジコードの RDATA を
  置かなければならない (MUST)。
- **FR-078**: 当該チャレンジコードに対応するラベルが存在しない場合は、追加しなければ
  ならない (MUST)。**RDATA が既に存在する場合も同様である (MUST)。**
  ラベルを持たない RDATA は回収の対象にならず、永久に残るため。
- **FR-079**: 既存のラベルの値を更新するのは、**残りの猶予が閾値を下回る場合に限る**
  (MUST)。閾値以上の残りがある場合は更新してはならない (MUST NOT)。
- **FR-080**: 閾値は猶予より短くしなければならない (MUST)。
- **FR-081**: 猶予は設定可能としなければならない (MUST)。既定は、同時に検証を行う
  実行が要する時間に対して十分な余裕を持ち、かつ蓄積を抑える長さとすること (MUST)。
  既定値は data-model.md の配備単位の設定に定める (猶予 1 時間、閾値はその 1/2)。

*後片付け (CleanUp)*

- **FR-082**: 後片付けにおいて、当該チャレンジの RDATA とラベルを削除しては
  ならない (MUST NOT)。期限による回収に委ねること (MUST)。

*変更が生じない場合*

- **FR-083**: **望む最終状態が現状と一致する場合、ゾーンへの変更を行ってはならない
  (MUST NOT)。** 排他の取得も反映も行わないこと (MUST)。
  「変更が生じる」とは次のいずれかを指す (MUST)。

  | 条件 | `Present` | `CleanUp` |
  |---|---|---|
  | 回収すべき期限切れがある | 変更する | 変更する |
  | 当該コードの RDATA が存在しない | 変更する | — |
  | 当該コードのラベルが存在しない | 変更する | — |
  | ラベルの残りの猶予が閾値を下回る | 変更する | — |
  | 上記のいずれでもない | **変更しない** | **変更しない** |

- **FR-084**: 変更の要否の判定は、排他を取得せずに公開レコードを読んで行ってよい (MAY)。
  判定の結果が「不要」であれば何も変更しないため、読み出しの時点の状態が古くても
  害がない。**ラベルの残りが閾値以上であれば、その RDATA が他の実行に回収されることも
  ないため、判定と実行の間に状態が変わる経路がない。**
- **FR-084a**: ロックを取得したのちに読んだ状態で、望む最終状態が既に成立していると
  判明した場合、反映を行ってはならない (MUST NOT)。先に走っていた処理が完了した直後の
  再試行などで起こる。ロックの取得と解放は行われるが、ゾーンのシリアルと変更履歴を
  動かさない。
- **FR-085**: 変更を行わずに終えた場合も、呼び出しは成功として返さなければ
  ならない (MUST)。望む最終状態が既に成立しているため。

**再試行への配慮**: 同一ゾーンに対するレコード操作は並行できないため、変更が不要な操作に
反映を費やすと、**再試行が重なった際に直列の待ち行列を作り、本来の処理を圧迫する。**
再試行の時点では元の提示が設定した期限がそのまま残っており、更新しても窓はほとんど
前進しない。閾値を設けるのは、この無益な反映を避けるためである。

*件数の上限*

- **FR-086**: ラベルの件数には DPF の上限 (10 件) がある。この枠は本サービス以外が
  付けたラベルと共有する。追加によって総数が上限を超える場合、要求を失敗させなければ
  ならない (MUST)。他者のラベルも本サービスの記録も追い出してはならない (MUST NOT)。
- **FR-087**: 上限に達したことをログに記録しなければならない (MUST)。
  到達は、猶予が長すぎるか、同一の名前に対する検証の失敗が繰り返されていることを示す。

**設計の背景**: 複数のクラスタが同一の ACME アカウントを共有して同一の名前の証明書を
取得すると、同一のチャレンジコードを受け取ることがある。後片付けの時点で RDATA を削除する
設計では、一方の後片付けが他方の検証中の RDATA を消す。

これを保持者の記録によって解く方法もあるが、**期限による回収は「誰も他人の RDATA を
消さない」という形で同じ問題を構造的に解消する。** 保持者の識別、記録の集合演算、
再試行をまたいだ識別値の安定性、取り残された後片付けが後続の提示を打ち消す危険が、
いずれも生じない。

**代償**: 使用済みの RDATA が期限まで残る。また回収は `Present` / `CleanUp` の内部でのみ
行うため、**当該の名前に対する操作が二度と来なければ回収されない。** 証明書の更新が
続く限りは、次の提示の時点で回収される。

**猶予の長さ**: 期限が守るのは「他の実行が検証中の RDATA を回収しない」ことだけである。
必要な窓は数分であり、各実行の提示が期限を前進させるため窓は滑る。一方、期限が長いほど
使用済みの記録が残り、ラベルの上限に近づく。検証が繰り返し失敗すると、そのたびに新しい
チャレンジコードが払い出されて記録が増えるため、**長すぎる猶予は上限への到達を招く。**

#### 可観測性

- **FR-088**: DPF がエラーを返した場合、その応答を全文ログに記録しなければならない (MUST)。
  長さで切り詰めてはならない (MUST NOT)。問い合わせ用の識別子が失われてはならない (MUST NOT)。
- **FR-088a**: DPF および Kubernetes API へ送った要求の内容を、原因の特定に足る範囲で
  ログに記録しなければならない (MUST)。少なくともメソッド、エンドポイントのパス、対象の
  ゾーン ID、要求本文を含む。アクセストークンおよびそれを含むヘッダを記録に含めては
  ならない (MUST NOT)。Secret の値を含めてはならない (MUST NOT)。
  - **ゾーン全体の一括置換の要求に限り、本文は要点に留めなければならない (MUST)。**
    本文はゾーン全体のレコードを含み、ゾーンの規模に比例して大きくなるため。要点とは、
    本サービスが加除したレコードの差分 (対象のレコード名、加除した RDATA、加除したラベル)
    と、送ったレコードの総数である。本サービスが変更するのはチャレンジレコードに限られる
    (FR-055) ため、原因の特定にはこの差分で足りる。
  - 一括置換以外の要求の本文は、切り詰めずに記録しなければならない (MUST)。
- **FR-088b**: FR-088 および FR-088a の記録は、ログとエラーに限らなければならない (MUST)。
  webhook の HTTP 応答の本文へ載せてはならない (MUST NOT)。
- **FR-089**: DNS レコードを変更する操作について、対象ゾーン・レコード名・操作種別・結果を
  ログに記録しなければならない (MUST)。
- **FR-090**: DNS レコードの変更操作の成否と件数を計測できなければならない (MUST)。
- **FR-091**: 要求の受信から DPF への呼び出しまでを 1 つのトレースとして追跡できなければ
  ならない (MUST)。
- **FR-092**: ゾーン名・レコード名・レコード値を、メトリクスのラベルおよびトレースの属性に
  既定で含めてはならない (MUST NOT)。
- **FR-093**: Kubernetes の liveness / readiness probe から利用できるヘルスチェックを
  提供しなければならない (MUST)。

### Key Entities

- **Solver 設定**: Issuer / ClusterIssuer の `dns01.webhook.config` に書かれる値。
  DPF の接続先と、アクセストークンの所在を表す。要求ごとに cert-manager から渡される。
- **DPF アクセストークン**: DPF API を呼び出すための認証情報。Kubernetes の Secret に
  置かれ、要求ごとに決まる namespace から読み出される。
- **DNS ゾーン**: DPF が管理する権威ゾーン。`ResolvedZone` (委任されたゾーン) と一致するものが
  1 つ選ばれる。チャレンジ対象の FQDN と longest match するゾーンを選ぶのではない。
- **ゾーン許可パターン (`domainFilters`)**: 変更してよいゾーンを表すパターンの並び。
  完全一致、`*.<ドメイン>` による配下の一括許可、`*` による全許可の 3 形式をとる。
  空のときは何も許可しない。設定誤りに対する歯止めであり、認可の境界ではない。
- **チャレンジコード**: cert-manager から与えられる、1 回のチャレンジに対応する値。
  TXT レコードの RDATA として 1 件追加され、期限を過ぎたのちの操作で回収される。
  後片付けの時点では削除されない。
- **チャレンジレコード**: cert-manager から与えられた FQDN の TXT レコード。通常は
  `_acme-challenge.<対象名>` だが、CNAME による委譲が使われている場合は委譲先の任意の
  名前となる。1 つのレコードが複数の RDATA を保持しうる。本サービス以外が置いた RDATA が
  含まれることもある。期限を過ぎたチャレンジコードに対応する RDATA だけが、
  次の操作の際に取り除かれる。
- **期限の記録**: チャレンジレコードのラベルの 1 エントリ。キーがチャレンジコードを
  識別する値を、値が期限を表す。**チャレンジコード 1 つにつき 1 エントリ**であり、
  保持者を区別しない。期限を過ぎたものが回収の対象になる。DNS には公開されない。
  レコードのラベルの上限 10 件を本サービス以外のラベルと共有する。
- **ゾーンロック**: DPF が提供するゾーン単位の排他制御。設定されたロックオーナーとともに取得され、
  変更の適用が完了したのちに解放される。ロックオーナーは、どの配備がゾーンを掴んでいるかを表す。
  状態はゾーンのラベルに置かれ、解放後もラベルを 1 つ消費し続ける。
- **変更の Description**: ゾーンの変更を適用するときに DPF へ残す記録。
  `by cert-manager(<ロックオーナー>)` の形式をとり、80 文字以内に収まる。
  どの配備が行った変更かを、DPF の変更履歴から判別するために用いる。
- **チャレンジ要求**: cert-manager から渡される 1 回の要求。対象 FQDN、委任されたゾーン
  (`ResolvedZone`)、チャレンジ値、要求元の namespace、および ClusterIssuer 由来かどうかの
  区別を含む。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 管理者は、アクセストークンの Secret と ClusterIssuer を用意するだけで、
  DPF 管理下のドメインの証明書を取得できる。追加のコード変更・独自スクリプトを要さない。
- **SC-002**: (削除) 変更 API の呼び出し回数による基準は置かない。ロックの取得だけで
  一時レコードの作成・ゾーンのラベルの変更・一時レコードの取り消しが動き、回数は
  `dpf-go` の実装で決まるため本サービスが制御できない。1 回の処理が要求のタイムアウトに
  達することを前提とし、収束を SC-027 で測る。
- **SC-003**: DPF のジョブ待ちを除いた本サービス自身のオーバーヘッドが、チャレンジ
  1 件あたり 5 秒以内である。
- **SC-004**: 操作期限に達したとき、操作期限を越えて DPF への書き込みが行われた件数が
  0 件である。
- **SC-005**: 呼び出し元のタイムアウトと再試行を経ても、記録の数と RDATA の数がずれた
  件数が 0 件である。
- **SC-006**: 証明書の更新を 10 回繰り返したあと、対象ゾーンに残るチャレンジ用の
  RDATA が**猶予の期間に生じたもののみ**であり、それ以前のものが 0 件である。
  使用済みの RDATA は期限による回収に委ねられ、後片付けの時点では残る。
- **SC-007**: 同一 FQDN に対する複数のチャレンジが並行して処理された場合でも、
  取得できた証明書の割合が 100% であり、期限を過ぎてから同一の名前を操作したのちに残る
  チャレンジ用 RDATA とラベルが 0 件である。
- **SC-008**: ある namespace の利用者が、他の namespace に置かれたアクセストークンを
  利用できる経路が 0 件である。
- **SC-009**: 失敗した 5 種類のチャレンジ (無効なトークン / Secret 不在 / key 不在 /
  ゾーン不在 / DPF 到達不能) について、Pod のログのみで原因を判別できる割合が 100% である。
- **SC-010**: kube-apiserver を経由せず Pod へ直接接続した場合の成功率が 0% である。
- **SC-011**: 同一ゾーンに対して、本サービスと**ゾーンロックに参加する**他のソフトウェア
  (本サービスの別の配備を含む) が同時に変更を行った場合に、一方の変更が失われる件数が
  0 件である。ゾーンロックに参加しない変更者 (管理画面からの編集など) の未反映の編集は
  対象外とする (Assumptions の「ロックに参加しない変更者」を参照)。
- **SC-012**: DPF のゾーン変更履歴を見ることで、本サービスが行った変更と、どの配備が
  行ったものかを判別できる割合が 100% である。
- **SC-013**: 本サービスを異常終了させたあと、ゾーンがロックされたまま残る件数が 0 件である。
- **SC-014**: 本サービスが付与した Description が 80 文字を超える件数が 0 件であり、
  切り詰められた件数が 0 件である。
- **SC-015**: `domainFilters` に一致しないゾーンに対してレコードが変更された件数が 0 件である。
- **SC-016**: `domainFilters` が空または未指定の状態で変更されたレコードが 0 件である。
- **SC-017**: `*example.jp` のようなラベル境界に揃わないパターンによって、`example.jp` の
  配下でないゾーン (`evilexample.jp` など) が変更された件数が 0 件である。
- **SC-018**: CNAME による委譲を使う構成において、委譲先のゾーンが `domainFilters` に
  一致しないにもかかわらずレコードが変更された件数が 0 件である。
- **SC-019**: 複数のドメインが同一の委譲先を共有する構成において、一方の後片付けによって
  他方のチャレンジコードが失われた件数が 0 件である。
- **SC-020**: 本サービス以外が置いた RDATA を持つ TXT レコードに対して提示と後片付けを
  10 回繰り返したあと、当初の RDATA がすべて元のまま残っている割合が 100% であり、
  TTL が変更された件数が 0 件である。
- **SC-021**: 複数のクラスタが同一の ACME アカウントで同一の名前の証明書を同時に取得した
  とき、一方の後片付けによって他方の証明書取得が失敗した件数が 0 件である。
- **SC-022**: 同一のチャレンジに対して後片付けを 2 回以上呼び出しても、他のチャレンジが
  必要としている RDATA が削除された件数が 0 件である。
- **SC-023**: 実行を途中で消滅させたあと、期限を過ぎてから同一の名前を操作したとき、
  残存したラベルとチャレンジ用 RDATA が取り除かれる割合が 100% である。
- **SC-024**: 証明書の取得を完了し、**期限を過ぎてから同一の名前を操作したとき**、
  対象ゾーンに残る本サービスのラベルとチャレンジ用 RDATA が 0 件である。
  本サービス以外が付けていたラベルは、すべて元のまま残っている。
- **SC-025**: 望む最終状態が既に成立している操作において、DPF への変更 API の

  ラベルが揃いラベルの残りが閾値以上の場合の双方を含む。
- **SC-026**: 同一のチャレンジに対する提示を閾値の期間内に 10 回繰り返したとき、
  ゾーンへの変更を行うのが **1 回目のみ**であり、2 回目以降の DPF への変更 API の
  呼び出し回数が 0 回である。
- **SC-027**: 1 回の処理が要求のタイムアウト (60 秒) を越えた場合でも、cert-manager の
  再試行を経て証明書の取得が完了する割合が 100% である。完了後の再試行による
  ゾーンへの変更が 0 件である。

## Assumptions

- cert-manager v1.21.2 以降が導入済みのクラスタで動作することを前提とする。
- 利用者は DPF の契約と、対象ゾーンのレコードを操作できるアクセストークンを保有している。
- DPF のゾーンおよびレコードの作成・変更・削除は DPF API 経由で行える。本サービスは
  ゾーンそのものの作成・削除を行わない。
- 本サービスは cert-manager の DNS01 solver としてのみ動作し、DNS レコードの
  一般的な同期 (external-dns 的な用途) は対象外とする。
- チャレンジ対象の FQDN は cert-manager から与えられる。本サービスが Certificate や
  Ingress を直接参照することはない。
- アクセストークンを保持する Secret は利用者が作成する。本サービスおよび配布物が
  トークンを含む Secret を作成することはない。
- **`domainFilters` のパターン形式 (設計判断)**: 利用者は「glob でマッチできる」ことを
  求めたが、本仕様は受け付ける形式を 3 つ (`*` / `*.<ドメイン>` / 完全一致) に限定した。
  一般的な glob では `*example.jp` が `evilexample.jp` に一致し、これは憲章が禁じる
  接尾辞一致そのものになる。ラベル境界に揃わないパターンは、単体では正しく動いて見えて
  特定の名前でのみ範囲判定をすり抜けるため、受け付ける形式を絞って解釈の幅を残さない。
- **複数クラスタからの同時利用 (利用者指定)**: 本仕様は、複数のクラスタが同一の ACME
  アカウントを共有する構成を想定する。同一のチャレンジコードが共有される場合の扱いは、
  **期限による回収**で解く。後片付けが RDATA を削除しないため、一方の後片付けが他方の
  検証中の RDATA を消すことがない。保持者を識別する必要がなく、記録はチャレンジコード
  1 つにつき 1 つのラベルで足りる。
- **使用済み RDATA の残存 (利用者判断)**: 上記の代償として、使用済みの RDATA は期限まで
  ゾーンに残る。cert-manager の `CleanUp` の文面 (`should remove any presented challenge
  records`) からは外れるが、`_acme-challenge` の TXT が一定期間残ることに実害はない。
  ACME サーバは期待する値の存在のみを確認する。
- **回収の遅延評価 (利用者判断)**: 回収は `Present` / `CleanUp` の内部でのみ行う。
  **当該の名前に対する操作が二度と来なければ回収されない。** 証明書の更新が続く限りは、
  次の提示の時点で回収される。常時動く回収処理は設けない。
- **記録の可視性**: 期限の記録はレコードのラベルであり、**DNS には公開されない。**
  別のレコードに記録を置く場合と異なり、進行中のチャレンジの存在が外部から観測される
  ことはない。DPF の API または画面から見える範囲に留まる。
  アクセストークンは含めない (FR-071)。
- **運用上の前提 (利用者判断)**: ACME 以外の用途で、チャレンジ名と同一の名前に TXT
  レコードが置かれることはほぼない。このため回収してよい時刻による記録の除去が、
  本サービス以外の RDATA に影響する危険は低い。ただし他の RDATA を保全する要件
  (FR-029, FR-033, FR-034) は維持する。前提が崩れた場合でも壊さないためである。
- **処理時間とタイムアウト (利用者指定)**: DPF の変更系 API は非同期で 1 回 10 秒以上を要し、
  同一ゾーンへのレコード操作は並行できない。ロックの取得だけで完了を待つ変更が 3 回動き、
  回数は本サービスから減らせない。**1 回の処理が要求の上限 60 秒に達することを前提とする。**
  処理は呼び出し元のタイムアウト後も完了まで進め、再試行が望む最終状態を見つけて
  変更を行わずに成功することで収束させる。`CleanUp` は回収すべきものが無ければ
  変更 API を 1 回も使わない。
- **ゾーン反映の時間 (利用者確認)**: ゾーン反映の所要時間は、編集していないレコードも
  含めたゾーン全体のレコード数に影響される。反映 1 回は避けられない固定費であり、
  その大きさは利用者のゾーンの規模に依存し本サービスでは制御できない。
- **ロックに参加しない変更者**: ロックが保証するのは **2 者が同時にロックを取得しないこと**
  であり、これはユーザ (アクセストークン) をまたいで成立する。**一方、ロックの保持中に
  他ユーザや管理画面からレコードを編集することは止められない。** その編集が未反映の
  状態にあれば、本サービスの適用によって失われうる。これは割り切る。
- **旧版との混在 (dpf-go v0.6.0 の制約)**: `dpf-go` v0.6.0 はロックの状態を SOA レコードの
  ラベルからゾーンのラベルへ移した。v0.5.0 以前を用いるプログラム (他の DPF 連携ツールを
  含む) と同じゾーンを操作すると排他が成立しない。同じゾーンを触るプログラムはまとめて
  更新する。
- **RDATA 単位の加除 (利用者指定)**: TXT レコードは複数の RDATA を保持しうる 1 つの
  リソースとして扱われる。本サービスはレコード全体を置き換えず、RDATA の集合に対する
  追加・削除として変更する。読み出しから書き戻しまでをゾーンロックの内側で行うことで、
  同一レコードに対する同時変更で RDATA が失われないようにする。
- **CNAME による委譲 (利用者指定)**: 書き込み対象のレコード名は限定しない。
  `_acme-challenge` が CNAME で委譲されている構成では、cert-manager が CNAME を辿った
  結果の FQDN が渡される。CNAME の解決は cert-manager 側が行い、本サービスは
  CNAME を辿らない。渡された FQDN をそのまま用いる。
- **`domainFilters` の位置 (利用者指定)**: `domainFilters` は Issuer / ClusterIssuer の
  solver 設定に置く。配備単位でクラスタ全体の上限を設ける仕組みは本仕様の対象外とする。
  テナント間の認可境界はアクセストークンであり、`domainFilters` はその内側の歯止めである。
- **ゾーンロック (利用者指定)**: ゾーンの排他制御には DPF が提供するゾーンロックを用いる。
  本サービス独自のロック機構を実装しない。DPF のロックに参加しない変更者が同一ゾーンを
  操作する場合、本サービスはそれを検知できない。
- **長さ制約**: Description は最大 80 文字 (DPF)、ロックオーナーは最大 32 文字 (`dpf-go`
  v0.6.0)。Description の形式 `by cert-manager(<ロックオーナー>)` は最大 49 文字であり、
  上限に余裕を持って収まる。いずれかの上限が変わった場合、本仕様の Description 形式を
  見直す必要がある。
- **ロックオーナーの既定値**: 本仕様はロックオーナーを必須設定とした。本サービスの名称のみでは
  複数クラスタを区別できず、区別可能な既定値を本サービスが推測すると、管理者が意図しない
  値でロックを取得することになるため。代替案として、クラスタを一意に識別できる値から
  既定値を導出する方法があるが、導出元の選定は plan で扱う。
- **実装上の制約 (利用者指定)**: 本サービスは cert-manager が提供する webhook 用の
  枠組み (`github.com/cert-manager/cert-manager/pkg/acme/webhook/cmd`) を用い、
  DPF 固有の処理を `webhook.Solver` の実装として与える。同じ契約を独自の HTTP サーバとして
  再実装しない。ゾーンロックの取得・解放には `github.com/iij/dpf-go` が提供するロック機能を
  用いる。具体的な構成は plan で定める。
- **憲章との整合**: ClusterIssuer 用の既定 namespace について、憲章 v3.0.1 が
  「本サービスが動作している namespace」へ改められ、本仕様と一致した。
