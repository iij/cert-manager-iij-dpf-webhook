# certmanager-iij-dpf-webhook Constitution

本プロジェクトは、Kubernetes の cert-manager に対して IIJ DNSプラットフォームサービス (DPF) を
DNS01用の プロバイダとして提供する webhook provider である。単一の Go 製 HTTP サービスとして実装される。

## Core Principles

### I. cert-manager Webhook 契約への準拠 (NON-NEGOTIABLE)

本サービスの外部インタフェースは cert-manager webhook provider API の仕様そのものであり、
独自拡張によってこれを逸脱してはならない (MUST NOT)。

- 上流仕様が定めるエンドポイント、HTTP メソッド、ステータスコード、リクエスト/レスポンスの
  JSON スキーマ、およびネゴシエーション用メディアタイプに完全に従うこと (MUST)。
- 仕様に対する解釈が必要な箇所は、実装コードではなく契約テストに落とし込み、テストを
  仕様の唯一の実行可能な表現とすること (MUST)。
- 上流仕様の変更に追随する場合は、まず契約テストを更新し、その差分をレビュー対象とすること (MUST)。
- cert-manager 本体が期待しない独自エンドポイントやフィールドを追加しないこと (MUST NOT)。
  DPF 固有の挙動が必要な場合は、設定またはアノテーション経由で表現し、契約は変更しない。

**根拠**: webhook provider は cert-manager 本体から見れば差し替え可能な部品である。契約から
外れた瞬間に本体のアップグレードで壊れ、利用者は原因を切り分けられない。契約遵守は本
プロジェクトの存在意義そのものであり、交渉の余地はない。

### II. プロバイダ境界の分離

DPF API へのアクセスは専用のクライアント層に閉じ込め、その外へ漏らさないこと (MUST)。

- HTTP クライアント、認証トークンの取り扱い、DPF 固有のリクエスト/レスポンス型、リトライ、
  レート制御は、すべて DPF クライアント層の内側に置くこと (MUST)。
- webhook ハンドラおよびドメインロジックは、DPF のトランスポート詳細 (URL、ヘッダ、
  ステータスコード、SDK 型) を直接参照しないこと (MUST NOT)。両者はインタフェースで結合する。
- DPF のエラーは、クライアント層で本プロジェクト固有のエラー型に変換してから上位へ返すこと (MUST)。
- クライアント層はインタフェース経由で差し替え可能とし、上位層のテストが実際の DPF API に
  到達しないこと (MUST)。

**根拠**: 契約 (原則 I) と外部 API という 2 つの変わりうる境界の間に本サービスは位置する。
両者を直接結線すると、どちらの変更もコード全体に波及する。境界を分離して初めて、DPF API を
モックしたテストが書け、TDD (原則 III) が現実的なコストで成立する。

### III. テストファースト (NON-NEGOTIABLE)

TDD を必須とする。テストを先に書き、失敗を確認してから実装すること (MUST)。

- 実装より前にテストを書くこと (MUST)。テストが期待どおり失敗することを確認してから
  実装に着手すること (MUST)。
- Red-Green-Refactor のサイクルをレビューで確認可能にすること (MUST)。コミットまたは
  PR の記述から、テストが実装に先行した事実を追跡できること (MUST)。
- バグ修正は、まず当該バグを再現して失敗するテストを追加することから始めること (MUST)。
  再現テストのない修正はマージしないこと (MUST NOT)。
- テストのない実装コード、および実装に合わせて後から書き起こしたテストは受け入れない (MUST NOT)。

**根拠**: 本サービスは DNS レコードという不可逆かつ広範囲に影響する状態を書き換える。手元での
再現が難しい本番障害を、リリース後に発見する余裕はない。テストファーストは、書かれる仕様の
量ではなく、仕様が実装より先に存在することを保証するための規律である。

### IV. DNS 変更の安全性

DNS レコードの変更は、常に「意図した範囲に限定され、繰り返し実行しても安全」でなければ
ならない (MUST)。

- すべての適用操作は冪等であること (MUST)。同一の変更セットを再適用しても、最終状態が
  変わらず、追加の破壊的副作用を生まないこと。
- domain filter およびゾーン絞り込みの対象外にあるレコードは、いかなる場合も変更・削除しない
  こと (MUST NOT)。範囲判定はレコードを書き込む直前に行うこと (MUST)。
- 範囲判定はドメイン名のラベル境界で行うこと (MUST)。文字列としての部分一致や接尾辞一致で
  判定しないこと (MUST NOT)。判定方法は「ドメイン名の取り扱い」の規定に従う。
- 変更適用中にエラーが発生した場合は fail closed とし、部分的に成功した状態を「成功」として
  cert-manager に返さないこと (MUST NOT)。エラーは握り潰さず上位へ伝播させること (MUST)。
- DPF API が変更の反映に明示的な適用 (commit) 操作を要求する場合、その完了までを一つの
  変更操作として扱い、未適用の変更を残したまま成功を返さないこと (MUST NOT)。
- 破壊的操作を伴う変更経路には、その挙動を検証するテストを必ず用意すること (MUST)。

**根拠**: 誤った DNS 変更は、対象サービスの全面停止に直結し、TTL の分だけ復旧が遅れる。
cert-manager は本サービスを無人で繰り返し呼び出すため、冪等性と範囲限定は運用上の心構えでは
なくコードで保証すべき性質である。

### V. 可観測性と運用性

障害発生時に、Pod のログと標準的な Kubernetes の操作だけで原因を切り分けられること (MUST)。
ログ・メトリクス・トレースの 3 種類のテレメトリを提供すること (MUST)。

*ログ*

- ログは構造化ログとし、標準出力へ出力すること (MUST)。標準出力への出力は常に有効であり、
  他の出力先の設定によって停止しないこと (MUST NOT)。
- 標準出力に加えて、OpenTelemetry 形式でのログ出力を提供すること (MUST)。
  送出は OTLP (gRPC) および OTLP/HTTP に対応すること (MUST)。
- ログレベルは設定で変更可能とすること (MUST)。
- DNS レコードを変更する操作は、対象ゾーン・レコード名・操作種別・結果をログに残すこと (MUST)。
- **外部 API がエラーを返した場合、その応答を全文記録すること (MUST)。**
  長さで切り詰めないこと (MUST NOT)。要約や抜粋で置き換えないこと (MUST NOT)。
- 外部 API へ送った要求の内容も、原因の特定に足る範囲で記録すること (MUST)。
  何を送ったか分からないままでは、拒否された理由を追えない。ただし認証情報および
  それを含むヘッダを記録に含めないこと (MUST NOT)。除外の範囲は後述の「共通」に従う。
- これらは**ログとエラーに限る**。HTTP 応答の本文へ載せないこと (MUST NOT)。
  応答本文に載せると、内部状態が呼び出し側へ漏れる経路になる。

*メトリクス*

- メトリクスは Prometheus 形式と OpenTelemetry 形式の 2 種類で提供すること (MUST)。
  - Prometheus 形式は `/metrics` エンドポイントで公開すること (MUST)。
  - OpenTelemetry 形式は OTLP (gRPC) および OTLP/HTTP での送出に対応すること (MUST)。
- 両形式が同一の計測値を表すこと (MUST)。形式ごとに異なる意味の値を持たせないこと (MUST NOT)。
- DNS レコードの変更操作について、成否と件数を計測できること (MUST)。

*トレース*

- トレースは OpenTelemetry 形式で提供すること (MUST)。送出は OTLP (gRPC) および
  OTLP/HTTP に対応すること (MUST)。
- cert-manager からのリクエスト受信から DPF API 呼び出しまでを 1 つのトレースとして
  追跡可能にすること (MUST)。

*共通*

- API トークン、認証情報、およびそれらを含むリクエストヘッダを、ログ・エラーメッセージ・
  メトリクス・トレースのいずれにも出力しないこと (MUST NOT)。この禁止は、外部 API の
  エラー応答を全文記録する要件に優先すること (MUST)。全文記録が認証情報の出力を伴う場合、
  当該の値のみを伏せ、それ以外を切り詰めないこと (MUST)。
- ゾーン名・レコード名・レコード値を、メトリクスのラベルおよびトレースの属性に
  既定で含めないこと (MUST NOT)。含める場合は明示的な opt-in とすること (MUST)。
  これらは基数が非有界であり、かつ認証なしに公開されうるため。ログへの出力は
  この制限の対象外とする。
- OTLP による送出は既定で無効とすること (MUST)。送出先が設定された場合にのみ有効化すること
  (MUST)。テレメトリの外部送出は明示的な許可を要する (原則 VI)。本原則が求める「提供」とは
  機能を備えることを指し、既定で送出が無効であることと矛盾しない。
- OTLP 送出先への接続では TLS 証明書の検証を既定で有効とすること (MUST)。
- テレメトリの送出失敗によって、DNS レコードの処理を停止させないこと (MUST NOT)。
  送出失敗はログに記録し、本来の処理は継続すること (MUST)。
- ヘルスチェック用エンドポイントを提供し、Kubernetes の liveness/readiness probe から
  利用可能にすること (MUST)。
- 設定は環境変数またはコマンドライン引数で与えること (MUST)。ただし認証情報はこれらで
  与えないこと (MUST NOT)。認証情報の取得経路は「セキュリティ: バイナリの既定拒否」が
  定める規定に従うこと (MUST)。設定値をイメージに焼き込まないこと (MUST NOT)。

**外部 API のエラー応答を切り詰めない根拠**: DPF のエラー応答は `request_id` を含み、
これがサポートへの問い合わせのキーになる。長さで切ると、末尾にあるこの値が失われ、
**問い合わせる手段そのものがなくなる**。状態コードだけを残しても、何が悪かったのかは
分からない。エラー応答は本来短く、全文を残してもログを圧迫しない。

**根拠**: エラー発生時に利用者が最初に見るのはログである。
何が起きたかがログから読み取れなければ、利用者は cert-manager 側と DPF 側のどちらに問題が
あるのかすら判断できない。ログだけでは「遅い」「たまに失敗する」といった継続的な劣化を
検知できないためメトリクスを、cert-manager から DPF API までのどの区間で時間や失敗が
生じたかを特定するためトレースを、それぞれ必要とする。標準出力を常時有効とするのは、
テレメトリ基盤が未整備または障害中の環境でも、最低限の調査手段を残すためである。

### VI. Default-Deny (NON-NEGOTIABLE)

バイナリと、上流チャートへ与える推奨 values の双方において、明示的に許可されていない
ものはすべて拒否すること (MUST)。許可は常に opt-in であり、拒否が既定である。

- 設定を与えなかった場合の既定動作は「何もしない・何も許さない」であること (MUST)。
  未設定を「すべて許可」と解釈しないこと (MUST NOT)。
- 権限・到達性・機能は、必要と判明したものだけを個別に開けること (MUST)。
  「とりあえず広く開けて後で絞る」順序を採らないこと (MUST NOT)。
- 既定値を緩める設定項目は、利用者が明示的に指定した場合にのみ有効になること (MUST)。
  緩和時はその旨を警告としてログに出力すること (MUST)。
- 設定の解釈に失敗した場合、または想定外の値を受け取った場合は、起動を中止すること (MUST)。
  既定値へフォールバックして起動を続行しないこと (MUST NOT)。

**根拠**: 本サービスは DNS という到達性の根幹を書き換える権限と、DPF API の認証情報を併せ持つ。
既定が許可であれば、利用者の設定漏れがそのまま全ゾーンへの書き込み権限や不要な露出になる。
設定漏れの結果は「動かない」であるべきで、「気付かないうちに広く開いている」であってはならない。
これは原則 IV (DNS 変更の安全性) を、DNS 以外の層まで一貫して適用したものである。

  (MUST)。

*操作*

- 正規化、比較、包含判定、ラベル分割には `github.com/miekg/dns` が提供する関数を用いること
  (MUST)。`strings` パッケージの関数 (`HasSuffix`, `TrimSuffix`, `Contains`, `Split`,
  `EqualFold`, `ToLower` など) でこれらを実装しないこと (MUST NOT)。
- 末尾ドットの付与・除去、および大文字小文字の変換を自前で実装しないこと (MUST NOT)。
  FQDN 化のみが必要な場合も `dns.CanonicalName` を用いること (MUST)。
- 名前の比較は、正規化名どうしの比較として行うこと (MUST)。比較のたびに
  大文字小文字を無視する比較関数を呼ぶ実装にしないこと (MUST NOT)。
- あるゾーンが別の名前を包含するかの判定には `dns.IsSubDomain` を用いること (MUST)。
  接尾辞一致で代用しないこと (MUST NOT)。
- ラベルの分割・数え上げには `dns.SplitDomainName` および `dns.CountLabel` を用いること (MUST)。
  区切り文字での分割で代用しないこと (MUST NOT)。エスケープされたドットを含むラベルを
  誤って分割するため。
- 外部から受け取った名前は、使用前に `dns.IsDomainName` で妥当性を検証すること (MUST)。
  検証に失敗した名前を管理対象として扱わないこと (MUST NOT)。
- ワイルドカード名は明示的に判定し、通常の名前と同じ経路で暗黙に処理しないこと (MUST)。
- 表示・ログ出力の整形目的で文字列操作を行うことは許容する。ただしその結果を、
  判定・比較・API へ渡す値として再利用しないこと (MUST NOT)。

**根拠**: ドメイン名の文字列比較は、原則 IV が禁じる「範囲外への書き込み」を直接引き起こす。
`strings.HasSuffix(name, "example.com")` は `evil-example.com` に一致し、`strings.EqualFold` は
DNS の大文字小文字規則と一致せず、ドットでの分割はエスケープされたラベルを壊す。
いずれも単体では動いているように見え、特定の名前でのみ範囲判定をすり抜ける。
判定を仕様準拠のライブラリに委ねることは、原則 VI (Default-Deny) を名前解決層で成立させる前提である。
内部表現を正規化名に固定するのは、比較の正しさを個々の呼び出し箇所の注意深さに依存させないためである。
表現が経路によって揺れる状態では、同一の名前が別物として扱われ、レコードの重複作成や
削除漏れという冪等性 (原則 IV) の破れとして現れる。

**DNS01 Challenge Provider**

対応対象は cert-manager v1.21.2 が定義する webhook provider API であり、その Go の仕様
(`https://pkg.go.dev/github.com/cert-manager/cert-manager/pkg/acme/webhook`) を契約の正とする (MUST)。

本サービスは cert-manager の DNS01 solver としてのみ動作する (MUST)。external-dns をはじめ
とする他の webhook provider 機構の API を、同一バイナリで併せて実装しないこと (MUST NOT)。
両者はエンドポイント・スキーマ・呼び出し主体のいずれも異なり、併存させると原則 I が定める

本サービスは Kubernetes の **APIService (集約 API サーバ)** として実装すること (MUST)。

- 本サービスを APIService として登録すること (MUST)。登録に用いる CA 証明書の配布経路を
  README に示すこと (MUST)。

**根拠**: 呼び出し主体を取り違えると、到達制御と認証の設計がまとめて誤る。集約層を経由する

**セキュリティ: バイナリの既定拒否**

原則 VI をバイナリの実行時挙動に適用した具体要件。

- domain filter またはゾーンの許可リストが未設定の場合、いかなるレコードも管理対象と
  しないこと (MUST)。未設定を「全ゾーンを管理」と解釈しないこと (MUST NOT)。
  管理対象が空である旨をログに出力し、サービス自体は正常に応答すること (MUST)。
- 取り扱うレコード種別は許可リスト方式とすること (MUST)。未知または未対応の種別を
  暗黙に通過させないこと (MUST NOT)。
- webhook エンドポイントは、kube-apiserver の集約層から Pod の外を経由して呼び出される。
  ループバックアドレスにのみバインドしないこと (MUST NOT)。同一 Pod 内のサイドカーとの
  通信を前提とした設計にしないこと (MUST NOT)。ポート番号は plan で定める。
- webhook エンドポイントは TLS でのみ待ち受けること (MUST)。平文で待ち受ける設定を
  提供しないこと (MUST NOT)。
- **呼び出し元の認証はクライアント証明書の検証によって行うこと (MUST)。** 集約層が提示する
  クライアント証明書を、クラスタの集約層向け CA に照らして検証すること (MUST)。
  検証に用いる CA をクラスタから取得すること (MUST)。イメージやチャートに焼き込まないこと
  (MUST NOT)。
- **有効なクライアント証明書を提示しない接続を、TLS ハンドシェイクの段階で拒否すること
  (MUST)。** kube-apiserver を経由せずに Pod へ直接到達した接続が、証明書検証エラーとなって
  要求に至らないこと (MUST)。証明書を提示しない接続を受け入れて、後段で判定する設計に
  しないこと (MUST NOT)。
- クライアント証明書の検証を無効化する設定を提供しないこと (MUST NOT)。開発用途を理由とした
  迂回手段も設けないこと (MUST NOT)。
- 到達範囲の制限を NetworkPolicy のみに依存しないこと (MUST NOT)。NetworkPolicy は
  多層防御の一層であり、クライアント証明書の検証の代替ではない。逆に、証明書検証が
  成立していることを理由に NetworkPolicy を省略しないこと (MUST NOT)。

**根拠**: 集約 API サーバへの到達制御は、NetworkPolicy だけでは完結しない。kube-apiserver は
多くのクラスタでホストネットワーク上の control plane ノードで動作し、namespace セレクタでは
送信元として表現できない。結果として ingress 規則が緩くなりがちで、同じクラスタ内の任意の
Pod から webhook ポートへ到達しうる。クライアント証明書の検証をハンドシェイク段階で必須と
するのは、この到達をそこで断ち切るためである。迂回手段を設けないのは、設けた時点でそれが
本番で有効化される経路になるからである (原則 VI)。
- exposed エンドポイントが返す情報は、healthz と metrics に限定すること (MUST)。
  exposed エンドポイントを webhook エンドポイントと同一のポートで提供しないこと (MUST NOT)。
  webhook エンドポイントはクライアント証明書の検証を要するが、probe とスクレイプは
  それを提示できない。ポート番号は plan で定める。
  ゾーン名・レコード値・設定内容など、DNS 構成が推測できる情報を認証なしで返さないこと
  (MUST NOT)。
- DPF API への接続では TLS 証明書の検証を常に有効とすること (MUST)。検証を無効化する
  設定を提供する場合、既定は有効とし、無効化時は警告をログに出力すること (MUST)。
- 起動時に必須設定の充足を検証し、不足していれば異常終了すること (MUST)。ただし DPF API の
  アクセストークンはこの検証の対象外とする。トークンの所在はリクエストごとに決まるため、
  起動時には確定しない。トークンが起動時に取得できないことを理由に起動を拒否しないこと
  (MUST NOT)。

*DPF API アクセストークンの取得*

- トークンは Kubernetes の Secret リソースから、Kubernetes API 経由で取得すること (MUST)。
- 取得元の namespace は、当該 ChallengeRequest の `AllowAmbientCredentials` によって決まる
  (MUST)。この値以外を根拠に取得元を決めないこと (MUST NOT)。

  | `AllowAmbientCredentials` | 要求の由来 | 読み取りを許す namespace |
  |---|---|---|
  | `false` | namespace に閉じた Issuer | `ResourceNamespace` のみ |
  | `true` | ClusterIssuer | ClusterIssuer が指定する namespace |

- `AllowAmbientCredentials` が `false` の場合、`ResourceNamespace` 以外の namespace から
  Secret を読まないこと (MUST NOT)。設定が他の namespace を指している場合、その設定を
  採用せず当該要求を失敗させること (MUST)。`ResourceNamespace` へ読み替えて処理を
  続行しないこと (MUST NOT)。読み替えは、利用者が意図した認証情報とは別のものを
  黙って使うことになる。
- `AllowAmbientCredentials` が `true` の場合に限り、ClusterIssuer の設定が指定する
  namespace の Secret を読んでよい (MAY)。指定がない場合は、**本サービスが動作している
  namespace** を用いること (MUST)。この既定は起動時設定で変更できるものとしてよい (MAY)。
  いずれの方法でも namespace が定まらない場合は、いずれの namespace も読まず
  要求を失敗させること (MUST)。未設定を「任意の namespace を許可」と解釈しないこと
  (MUST NOT)。
- 取得元の Secret 名は ChallengeRequest の設定で指定されたものとし、指定がない場合は
  既定値 `dpf-token` を用いること (MUST)。既定値は Secret 名にのみ適用され、namespace の
  既定値としては用いないこと (MUST NOT)。
- トークンを環境変数およびコマンドライン引数から受け取らないこと (MUST NOT)。
  環境変数は Pod の情報表示やプロセスの環境から読み取れ、Kubernetes API 経由での
  Secret 取得と同じ保護水準を満たさないため。
- 取得したトークンをディスクへ書き出さないこと (MUST NOT)。プロセスのメモリ内に留めること
  (MUST)。
- 外部でトークンがローテーションされた場合、再起動なしに新しいトークンが使われること (MUST)。
  取得結果をキャッシュする場合、ローテーションが反映されない期間を有限に保つこと (MUST)。
- トークンの取得に失敗した場合、当該 ChallengeRequest を失敗として返すこと (MUST)。
  失敗を握り潰して成功を返さないこと (MUST NOT)。
  - Secret または鍵が存在しない、値が不正であるなど、同じ要求を繰り返しても解消しない失敗は
    恒久的な失敗として扱い、再試行しないこと (MUST)。
  - Kubernetes API への到達失敗など一時的な失敗は、上限を定めた再試行の対象としてよい (MAY)。
    上限のない再試行を行わないこと (MUST NOT)。
  - 恒久と一時のいずれに分類したかをログに残すこと (MUST)。
- トークンの値、およびトークンを含む Secret の内容を、エラーメッセージに含めないこと
  (MUST NOT)。

**根拠**: トークンの所在を ChallengeRequest ごとに決めることで、一つの webhook が複数の
namespace の利用者に対して、それぞれの認証情報で動作できる。

取得元を `AllowAmbientCredentials` で分けるのは、この値が「要求を出した Issuer が
namespace に閉じているか」を表すためである。namespace に閉じた Issuer は、その namespace の
利用者が作成できる。ここで他 namespace の Secret を読めてしまうと、自分の namespace に
Issuer を 1 つ作るだけで、任意の namespace の認証情報を読み出せる。namespace の境界が
認証情報の境界でなくなり、クラスタ内の権限分離が成立しなくなる。

ClusterIssuer はクラスタ管理者のみが作成できるため、その設定が指す namespace を
信頼してよい。この非対称性は cert-manager 本体が `AllowAmbientCredentials` で表明している
ものであり、本サービスが独自に判断する余地はない。判定を自前の設定値や要求内の
他のフィールドで代替しないのは、そこに解釈の幅が生まれた時点で上記の分離が破れるためである。

起動時検証からトークンを外すのは、リクエスト時に決まる値を起動時に検証できないためである。
検証できないものを必須設定として扱うと、「認証情報が未設定のまま起動しない」という規定が
実際には何も検証しないまま形骸化する。

    送信元を NetworkPolicy で表現できない。その場合も ingress を全開放しないこと
    (MUST NOT)。表現できる範囲で最も狭い規則を既定とし、表現しきれない旨と、
    その残余をクライアント証明書の検証が担うことを README に記載すること (MUST)。
  - Kubernetes API server への egress を許可すること (MUST)。トークン取得に必要なため。
  - DPF API への egress を許可すること (MUST)。
  - DNS 解決に必要な egress を許可すること (MUST)。
- OTLP 送出先への egress は、送出先が設定された場合にのみ許可すること (MUST)。
  OTLP を使わない利用者の NetworkPolicy に、テレメトリ用の穴を既定で開けないこと (MUST NOT)。
- 上に列挙した以外の egress を既定で許可しないこと (MUST NOT)。
- exposed ポートへの ingress は、probe とスクレイプに必要な送信元に
  限定すること (MUST)。全ての送信元に開放しないこと (MUST NOT)。
- `/healthz` と `/metrics` は同一ポートで提供されるため、NetworkPolicy で両者を区別できない。
  probe を通す設定は同時に `/metrics` を同じ送信元へ露出させる。この前提のもとで、
  メトリクスに機微な値を含めない要件 (原則 V) を満たすこと (MUST)。
- CPU・メモリの requests と limits を既定で設定すること (MUST)。
- 認証情報をリポジトリ、イメージ、およびチャートの既定 values に
  含めないこと (MUST NOT)。平文の値を values に書かせる例を示さないこと
  (MUST NOT)。トークンを環境変数として Pod に渡す例を示さないこと (MUST NOT)。
  トークンを保持する Secret をチャートが作成しないこと (MUST NOT)。利用者が
  自ら作成した Secret を参照する形とすること (MUST)。
- 上記のいずれかを緩和する設定は、既定 values では安全側に置き、必要な利用者が
  自ら上書きする形とすること (MUST)。

## 開発ワークフローと品質ゲート

- 変更は Pull Request 経由で行い、レビュー承認なしに main へマージしないこと (MUST NOT)。
- レビュアは、当該 PR が本 constitution の各原則に適合しているかを確認すること (MUST)。
  特に原則 III (テストが実装に先行したか)、原則 IV (範囲限定・冪等性)、
  原則 VI (既定値が拒否側か) を明示的に確認する。
- 設定項目またはチャートの values を追加する PR は、その既定が拒否側であることをレビューで
  確認すること (MUST)。既定を許可側に変更する PR は、理由を記載すること (MUST)。
- RBAC の権限、および NetworkPolicy の許可範囲を広げる PR は、その必要性をレビューで
  確認すること (MUST)。理由の記載のない拡大をマージしないこと (MUST NOT)。
- トークン取得元の namespace 判定に触れる PR は、`AllowAmbientCredentials` が `false` の
  経路で `ResourceNamespace` の外へ到達しうる変更が含まれていないことをレビューで
  確認すること (MUST)。
- TLS 設定およびクライアント証明書の検証に触れる PR は、証明書を提示しない接続が
  受理されうる変更が含まれていないことをレビューで確認すること (MUST)。
- **利用者に見える挙動を変更する PR は、`CHANGELOG.md` の更新が同じ PR に含まれている
  ことをレビューで確認すること (MUST)。** README との食い違いが生じる場合は、README の
  更新も含まれていることを確認すること (MUST)。可能であれば、利用者に見える契約に
  対応するファイルが変更された PR で `CHANGELOG.md` の更新を求める検査を自動化すること
  (SHOULD)。ただし「利用者に見えるか」は機械的に判定できないため、自動化は補助であり
  レビューの代替ではない。
- テストおよび CI の ACME サーバの接続先に触れる PR は、本番環境の ACME サーバへ
  接続しうる変更が含まれていないことをレビューで確認すること (MUST)。
- ドメイン名を扱うコードを追加・変更する PR は、`strings` パッケージによる判定が
  含まれていないことをレビューで確認すること (MUST)。可能であれば、この検出を
  `golangci-lint` の設定として自動化すること (SHOULD)。
- CI は以下をすべて通過することをマージの条件とすること (MUST):
  - シークレットの混入検査 (`betterleaks` による履歴の走査)
  - 整形の検証 (`gofmt -l ./...` の出力が空であること)
  - 全 Go ファイルに SPDX ヘッダが存在することの検証
  - ビルド (`go build ./...`)
  - 静的解析 (`golangci-lint run`)
  - 脆弱性検査 (`govulncheck ./...`)
  - 全テスト (`go test ./...`)
  - cert-manager webhook API の契約テスト
  - 既定設定での起動時挙動の検証 (domain filter 未設定時に管理対象が空であること、
    必須設定の不足時に異常終了すること、webhook エンドポイントが平文で待ち受けないこと)
  - **クライアント証明書検証の検証。** 次のいずれの接続も TLS ハンドシェイクの段階で
    拒否され、要求が処理されないことを確認すること (MUST)。
    - クライアント証明書を提示しない接続
    - 集約層向け CA 以外で署名された証明書を提示する接続
  - チャートが既定で生成する RBAC が、用途 1 (Secret の `get`) と用途 2 (集約 API サーバ) の
    いずれかに属する権限のみであることの検証。Secret に `list` / `watch` / 書き込み動詞が
    含まれないこと、およびワイルドカードを含まないことを確認すること (MUST)
  - トークン取得元の namespace 判定の検証。`AllowAmbientCredentials` が `false` の要求が
    `ResourceNamespace` 以外の Secret を読めないこと、および RBAC 上は読める状態にあっても
    読まないことを、いずれも確認すること (MUST)
  - チャートが既定で生成する NetworkPolicy が、列挙された通信のみを許可することの検証
  - 配布バイナリの ASLR が有効であることの検証
  - コンテナイメージのビルド、および脆弱性スキャン
  - 依存ライセンスの検査 (許容リスト外の依存がないこと)
  - イメージへのライセンス同梱の検証 (`/licenses/` に本体と依存の本文があること)
  - OCI アノテーションの検証 (`org.opencontainers.image.licenses` が正しいこと)
  - テストと CI が用いる ACME サーバが本番環境でないことの検証 (「ACME サーバの利用」を参照)
- `govulncheck` とコンテナイメージの脆弱性スキャンは、PR 時に加えて定期的に実行すること
  (MUST)。コード変更がなくても新たな脆弱性は公開されるため、PR 時の実行だけでは
  検出が漏れる。
- CI で用いる Go、`golangci-lint`、`govulncheck` のバージョンを固定すること (MUST)。
  ツールの暗黙のバージョン更新によって、同一コードの判定結果が変わる状態にしないこと
  (MUST NOT)。
- 原則から逸脱する実装を行う場合は、その理由と代替案を検討した結果を PR に記載すること (MUST)。
  記載のない逸脱はマージしないこと (MUST NOT)。
- 複雑さは正当化を要する。より単純な代替が存在する場合、単純な方を選ぶこと (MUST)。

### 実環境での検証

モックに対するテストは、変換と分岐の正しさを示すが、DPF が実際に何を受け付けるかは
示さない。API スキーマの解釈違い、制約の見落とし、非同期ジョブの挙動は、
実際に叩いて初めて分かる。

- **`main` へマージする前に、実際の DPF に対してレコードの追加・変更・削除を
  CI で実行し、成功することを確認すること (MUST)。** 手元での確認をもって
  代えないこと (MUST NOT)。手元の環境は再現性がなく、他の変更者が同じ確認を
  繰り返せない。
- 検証には破壊的操作を行ってよい**検証用ゾーン**を用いること (MUST)。
  本番ゾーンに対して実行しないこと (MUST NOT)。
- 検証は少なくとも次を含むこと (MUST)。
  - レコードの**追加**が反映されること
  - レコードの**変更**が反映されること
  - レコードの**削除**が反映されること
  - 同一の変更を再適用しても最終状態が変わらないこと (原則 IV の冪等性)
- **この検証を並列に実行しないこと (MUST NOT)。** 同時に走らせる場合、
  後続の実行を待たせること (MUST)。

**根拠**: 並列実行を禁じるのは、検証用ゾーンが共有される状態だからである。
2 つの実行が同時に走ると、それぞれがゾーンを読み、マージし、書き戻す。ゾーンに対する
機械的な変更者が、互いのロックに参加しないまま 2 つ並ぶ状況であり、変更を取り消し合う。

ゾーンロックによって書き込み自体は直列化されるが、それでは足りない。検証は
ゾーンの内容に対して表明を行うため、一方の実行が作ったレコードが他方の
表明に混ざる。判定が実行のタイミングに依存し、失敗が再現しなくなる。

### ACME サーバの利用

本サービスの検証の多くは DPF に対して行えるが、証明書の取得を端から端まで確かめる場合は
ACME サーバとの通信を伴う。

- **本プロジェクトのテストおよび CI で ACME サーバと通信する場合、本番の証明書を発行する
  本番環境の ACME サーバを用いないこと (MUST NOT)。** 公的に信頼される証明書を発行しない ACME サーバ
  (認証局が提供するステージング環境、またはテスト用に立てた ACME サーバ) を用いること (MUST)。
- 本番環境の ACME サーバの接続先は閉じた集合として plan に列挙すること (MUST)。テストと CI の
  設定がそのいずれかを指している場合、CI を失敗させること (MUST)。接続先の指定が無い場合に
  本番環境へ既定で接続する構成にしないこと (MUST NOT)。
- 本番環境の ACME サーバを用いる必要があると判断した場合も、テストや CI の一部として
  実行しないこと (MUST NOT)。利用者の環境で行う運用上の確認として扱う。
- 本規定の対象は、本プロジェクト自身のテストと CI に限る。利用者が本サービスを用いて
  証明書を取得する手順 (README や導入手順に示す Issuer / ClusterIssuer の例を含む) は
  対象としない。利用者の環境では本番環境の ACME サーバを用いることが本来の用途である。

**根拠**: 本番環境の ACME サーバが発行した証明書は公的に信頼され、Certificate Transparency の
ログに記録されて公開される。検証用ゾーンの名前が公開の記録に残り、失効させない限り
有効な証明書が手元に残る。また本番環境にはアカウントと名前ごとの発行数の制限があり、
繰り返し実行される CI が制限に達すると、同じアカウントや名前を使う本番の運用が
証明書を取得できなくなる。

## Governance

- 本 constitution は、本リポジトリにおける他のあらゆる慣習・慣行に優先する (MUST)。
  個別の判断が本文書と矛盾する場合、本文書が優先する。
- 改訂は Pull Request で提案し、内容の合意を得たうえでマージすること (MUST)。改訂 PR には
  変更理由と、既存コード・既存 spec への影響 (移行が必要な場合はその手順) を記載すること (MUST)。
- バージョニングは SemVer に従う (MUST):
  - MAJOR: 原則の削除、または後方互換性のない再定義を行った場合。
  - MINOR: 原則やセクションを追加した場合、または指針を実質的に拡張した場合。
  - PATCH: 文言の明確化、誤字修正など、意味を変えない改訂。
- 改訂時は `**Version**` 行と `**Last Amended**` を必ず更新すること (MUST)。
  `**Ratified**` は初回批准日であり、変更しないこと (MUST NOT)。
- 本文書には「守るべき結果」を記載すること (MUST)。ある選択の帰結として導かれる
  実装手段 (ビルドフラグ、Dockerfile の具体的な記述、呼び出しの順序や引数の組み立て方) は
  plan に置き、本文書に書かないこと (MUST NOT)。手段を本文書に書くと、その変更のたびに
  改訂手続きが必要となり、規範と実装詳細の区別が失われる。

*記載先の判定*

ある事項をどこに書くかは、**その値が変わったときに何が必要になるか**で決めること (MUST)。

| 変わったときに必要なもの | 記載先 |
|---|---|
| 本文書の改訂 | 本文書 |
| 実装の変更のみ | spec / plan |
| 何も要らない (時点ごとの観測値) | CI の出力 |

- 具体値・一覧・実測値を本文書に書くのは、その値からの逸脱がそのまま原則の破れになる場合に
  限ること (MUST)。そうでない値は、それが「閉じていること」だけを本文書に書き、
  閉じた集合の中身は plan に置くこと (MUST)。閉じていることの検証を CI に置くこと (MUST)。
- **本文書に TODO を書かないこと (MUST NOT)。** 「未定」は規範になりえない。規範として
  書けない事項は規範ではなく設計判断であり、spec または plan に属する。未確定の事項が
  あるまま本文書を確定させる場合、確定しているのは「何が閉じているか」であって
  「閉じた集合の中身」ではない。
- 上記の例外として、**特定のライブラリ・ツール・API の採用そのもの**、および
  **判定や正規化をそれらに委ねる範囲** は本文書に書いてよい (MAY)。これらは手段ではなく、
  逸脱が原則の破れに直結する結果だからである。たとえば「ドメイン名の判定を
  `github.com/miekg/dns` に委ね、`strings` で実装しない」は原則 IV と VI の成立条件であり、
  plan 側の裁量に置けない。どの関数を用いるかまでを本文書に書くのは、代替実装が
  容易に書けてしまい、書かれた時点で原則が破れる場合に限ること (MUST)。
- 実行時の開発ガイダンス (ディレクトリ構成、コーディング規約、頻用コマンド) は
  リポジトリルートの `CLAUDE.md` に置き、本文書とは分離すること (MUST)。
  本文書は「何を守るか」を、`CLAUDE.md` は「どう作業するか」を扱う。
